**Headline.** A market is the two-letter country code, stored as `char(2)` in five strategy tables and as a jsonb array of codes on `waves.markets`. There is **no markets table**. Nothing reads a market's country for anything but a label (`labelForCountryCode`). The campaign side does not read the wave's markets. No PL migration is on `main` or in production.

## 2. The campaign side: does anything on a linked campaign read the wave's markets?

**No.** Evidence:

1. The campaign's `wave` object (`app/Modules/Campaigns/Http/Resources/CampaignResource.php:112-125`) carries `id`, `name`, `go_live_on`, `status`, `link_locked`. It has **no markets**.
2. `rg "->markets|wave.*markets|markets.*wave" apps/api/app` outside `Waves/` and `Strategy/` finds one hit: the audit key list in `AuditPayloadKeys.php:82`.
3. The Boards module touches waves (`WaveInviteOrigin`, provisioning, card moves) but has no market or country read (`rg market|countr` over `Boards/Services` returns nothing).
4. `campaigns.listing_regions` (`Campaign.php`, `CreatorJobBoardController.php`, `CampaignController.php`) is a separate, campaign-owned list of ISO codes. Nothing copies a wave's markets into it or the other way round.
5. On the web, the only reader of `wave.attributes.markets` outside the waves and strategy modules is `BrandWavesPanel.vue:53`.

So changing what a wave market is cannot change a campaign, the board or the creator job board.

## 4. Erasure, audit and tenancy for the new tables

- **Erasure.** Every table must have a rule in `ErasureRegistry` (`ErasureRegistrySchemaTest`, `ErasureSelectionsCoverageTest` enumerate them). The new tables hold an agency-typed market name, a short code and ISO country codes: no creator or user data. Decision: `NotApplicable`, "Agency-authored (section 3.7), planning data about a brand's wave", with the typed `name` column decided as not personal in the same way as `wave_personas.name` (an agency-typed label, not a person). Same commit as the migration.
- **Audit.** Market create, rename, country change and removal are written as part of `wave.created` / `wave.updated` (one row per request, as now). The literal keys are read statically by `AuditPayloadKeysGuardTest`; today `markets` is decided (`AuditPayloadKeys.php:82`). The plan keeps `markets` (now the list of short codes), adds one key for the countries, and never puts a market **name** in a payload (names are free text, like a persona name). Strategy payloads keep the key `market`; its value becomes the market's short code (or ulid; see plan section 3.6). Each new key gets its Erasure decision in the same commit.
- **Tenancy.** The new tables carry `agency_id` and the `BelongsToAgency` scope like every wave child; markets are only reached through `agencies/{agency}/brands/{brand}/waves/{wave}`. A second agency must get 404, not 403, for another agency's market ulid.

## 6. Facts the plan depends on (one place)

1. A market's country is **display only** today: `labelForCountryCode` in the tabs, titles, dialogs and the refusal text. No query, filter, language or creator logic reads it (`rg labelForCountryCode` in `modules/strategy` and `modules/waves`; no backend reader).
2. **A market with only matrix cells cannot exist without personas**: a cell's foreign key `(wave_id, market, persona_id)` to `wave_personas` is RESTRICT (`wave_matrix_cells` migration `:51-52`), and deleting a persona removes its cells in `PersonaService` (`cells_removed` in the audit payload). Concepts also need a persona (`wave_concepts` `:40-41`). So "has personas" is the only gate needed; the concept count is for the message.
3. **Concept image keys do not contain a market** (`ConceptImageStorage.php:17-23`).
4. **Persona codes** are `string(8)`, unique per (wave, market) (`create_wave_personas_table.php:52`, `:67`); the default is `<market code><slot>` with `A..Z` suffixes on a clash (`PersonaService.php:311-317`).
5. **The wave row lock** (`lockForUpdate` in `WaveService::update`, and first in every strategy write) already serialises markets with everything under them.
6. `COUNTRY_OPTIONS` has English labels only; the API has no country names. A market name typed by the strategist is free text and is not translated.
7. The Creator model has `country_code` (`Creator.php:42`), which is what the PL-3 creator picker will match against a market's countries; script languages will be derived from the same countries (PL-3).
