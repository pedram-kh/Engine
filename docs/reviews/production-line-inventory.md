### N3. Where the design meets a standing rule

- **Tenancy** (`docs/security/tenancy.md` §3-§4; `PROJECT-WORKFLOW.md` §5.21): a portal member is not a `User` with an agency membership, so `tenancy.agency` passes non-users through (`SetTenancyFromAgencyRoute.php:63-65`) and `BelongsToAgencyScope` becomes a no-op without context (`BelongsToAgencyScope.php:33-35`). A portal route group has no precedent in the allowlist, and no test diffs routes against it, so conformance is by review only. "Editors see agency work across brands" and "one portal per brand" both need an explicit rule about whose agency and whose brand is in context. The policy `membership()` helper ignores the route agency (F2), which matters once a third role can hold a membership.
- **Erasure** (`ErasureRegistry.php:9-21`, `RegistryVerifier.php:52,94-98`): any new table must be classified or CI fails; any FK to `users` must be declared. Eligibility is creator-only (G5), so portal members (name, email, cookie, comments, drawings, approval records with names) have no deletion path. Audit scrub S1 to S5 key on `actor_type = 'user'`. Approval records and client comments are evidence that the design says carry "their name on every comment and decision", which conflicts in principle with an erasure-by-anonymisation default; the registry would need a disposition decided per table.
- **Schema-only migrations** (`PROJECT-WORKFLOW.md` §5.40): "Copy from a previous wave" (design frame 09), seeding the default editor or portal data, backfilling a `kind` on existing campaigns, and per-kind board columns for existing campaigns are all data operations and must be artisan commands with `--dry-run`. A `kind` column needs a default that makes a backfill unnecessary (the AH-069 shape). Board provisioning is lazy today (`BoardService.php:43-65`), so a per-kind column set provisioned the same way needs no row write for new campaigns; existing boards keep their current columns. The AH-041 backfill is not a pattern to copy.
- **24 locales** (`WORKING-PROCESS.md` §4): the design is English dark-only and the portal language is unstated (`new-sections-design-review.md` §7). The repo has no MT generator (K), so the "real MT baseline at merge time" rule for the flaky 10 has no tool in the repo to meet it. Notifications add two ×24 files per type (H5). Script content in two or three languages per market is data, not UI, and is outside this gate.
- **Theme:** the designs are dark only; the agency app has `agency-dark` and `agency-light` (K). Both must be built or light dropped by ruling.
- **New emails and notifications to real users** ship flag-gated, default OFF (`WORKING-PROCESS.md` §5): a module with about 20 new types needs per-section flags (none exist) and dry-run previews.
- **Production-data safety** (§5.40): every table in this inventory is additive; the risk is in the first data command per section. Pre-deploy snapshot and the unverified restore posture apply (`PROJECT-WORKFLOW.md` §5.40 standing item).
- **Role-check hygiene:** `AgencyLayout` renders all ten nav items to all roles (F4), so an editor shell cannot be a nav filter; it needs a separate layout, and `requireAgencyUser` passes any non-creator user (`guards.ts:306-327`), so an editor can reach every agency route unless a guard is added to each. The count to review is 27 backend and 24 SPA sites (F5).
- **Rulings that need a code definition before a plan:** ruling 3 leaves "Send to client" and the "Client review" stage on frame 13 without a meaning; ruling 5 leaves how an ad is placed in a month open; ruling 7 leaves the editor access path open. `AgencyRole` is per agency (`agency_users` unique `(agency_id, user_id)`), so "editors are agency staff" and "an open pool across brands" are consistent only inside one agency.
