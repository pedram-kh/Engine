### 2.2 The progress object (ruling Q1 of PL-1, unchanged by this sprint)

`WaveTrackerCalculator::progress` reads the six `STRATEGY` rows of **one** wave and returns `segments` (six of `done` / `in_progress` / `empty`), `label_kind` (`complete`, `not_started`, `step`) and `step_name` (the current name of the first row that is not done). A missing row reads `empty`. The other 18 steps never matter. Two callers: `WaveTrackerPresenter::tracker` (the wave page) and `progressForWaves` (the Brand page list in `WaveController` line 68, and the single wave in `WaveResource` line 39). Both read **stored rows only**: one grouped query on `wave_steps` for the whole list.

### 2.3 How a row is updated today

- The only writer of a status is `WaveStepService::applyStatus`: it sets `status`, **always sets `status_source = manual`**, sets `completed_on` to the actor's today when the new status is `done` and clears it otherwise. It runs inside `update` (step row locked, then `save`, audit `wave_step.updated` with before and after snapshots including `status_source` and `completed_on`).
- Roles: any agency user may set a status (the `PATCH` is open to all three roles; rename and move are admin and manager and a strategy step may not move stream: `stepStrategyLocked`).
- `System` is written only at provisioning and at stream add (the initial `not_started`). **No code path anywhere sets `in_progress` or `done` as `system`.**
- No strategy service touches `wave_steps` (grep of `app/Modules/Strategy`: no reference to `WaveStep`). The boundary Waves to Strategy today is one contract, `WaveMarketGuard` (`personaCountsByMarket`, `conceptCountsByMarket`, `renamePersonaCodes`), bound in `StrategyServiceProvider` and implemented by `StrategyWaveMarketGuard`. There is no contract the other way (Strategy to Waves). PL-2.5 needs one (plan section 1.5).

## 3. Where each real step's state can be computed from, and what it costs

"Per market" steps need one number per market. Existing code and tables:

| Step     | Data                                                                                                                                                                 | Query that exists today                                                                                                                                              | Cost for one wave (tracker)          | Cost for a list of N waves                |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ | ----------------------------------------- |
| USPs     | `wave_usps` (per wave; limits 6 max, warn below 4)                                                                                                                   | `WaveUsp::where(wave_id)->count()` in `StrategyController::show`                                                                                                     | 1 count                              | 1 grouped query on `wave_id`              |
| Personas | `wave_personas` (per market; min 2, max 8)                                                                                                                           | grouped `market_id, count(*)` in `StrategyController::show` and `MatrixService::progress`                                                                            | 1 grouped query                      | 1 grouped query on `(wave_id, market_id)` |
| Matrix   | `wave_matrix_cells` (unique `(persona_id, usp_id)`; per market through the persona)                                                                                  | grouped `market_id, count(*)` in `MatrixService::progress`; "cells to set" = personas x USPs per market                                                              | 1 grouped query (plus the two above) | 1 grouped query                           |
| Concepts | `wave_concepts.status` (`awaiting`, `approved`, `changes_requested`; the current status is stored on the concept; decisions are history in `wave_concept_decisions`) | `ConceptService::summary`: one grouped query `market_id, status, count(*)`; already yields `complete` per market (total > 0 and all approved) and `markets_complete` | 1 grouped query                      | 1 grouped query                           |
| Markets  | `wave_markets` of the wave                                                                                                                                           | `$wave->markets` relation                                                                                                                                            | 1 (already loaded for the page)      | 1 `whereIn`                               |

`StrategyController::show` already assembles all of this for one wave in about five queries (it feeds today's stepper counts). Reading the real state of **every** strategy step for a **list** of waves on read would add about five more grouped queries per list page, flat in N (no N+1), but the Brand page and the wave list would no longer be a single query on `wave_steps`. That is why the plan recommends storing the row and writing it when the step changes (plan section 1.5).

There is **no completion data today**: nothing records that a strategist finished a step. "Mark as complete" (ruling K1) needs a new table. Concepts need none: done is derived from `wave_concepts.status`.

Not computable today: `ugc.creators` and `ugc.scripts` have no data until PL-3 (ruling F1: hand-set).

## 5. Erasure, audit and tenancy for notes

- **Registry.** `ErasureRegistry` classifies every table (`RegistryVerifier` fails the build on an unclassified one). Precedent for agency-authored text: `wave_usps`, `wave_personas`, `wave_steps` are `Disposition::NotApplicable` ("Agency-authored (§3.7)") with a per-column note for each free-text column. `wave_concept_decisions` is the closest precedent for text an agency user typed **about a third party**: `NotApplicable`, `recorded_by_user_id` listed as the user reference, and `client_name`, `note`, `comment` each documented as free text about a person, with tech-debt 48 recording that the privacy documents need a sentence and that PL-4 decides how the name links to a user.
- **What erasing the author does.** The erasure pipeline erases **creators** (the `users` row is the anchor "never deleted" and anonymised). Agency members are `agency_users` (`NotApplicable`: "a creator is never a row here"); an agency user is not erased by this pipeline. If a user row is hard-deleted, the foreign key on every authored table is `nullOnDelete` (as `wave_concept_decisions.recorded_by_user_id`): the note stays, the author becomes null, the screen shows "Former member" (the `owner_is_former` precedent of `WaveTrackerPresenter`: a user whose membership is soft-deleted or not accepted is shown as former, and the name is not returned).
- **Free text that names a person** (a creator, a client contact, a colleague): not scanned, not redacted by the creator erasure (same as concept decisions). It is the agency's own business record. Recorded as a tech-debt row with the same sentence for the privacy documents (plan section 4).
- **Audit.** Metadata keys are literal (`AuditPayloadKeysGuardTest` reads them statically) and are listed in `AuditPayloadKeys`. Precedent in the Strategy module: ids, status, counts and booleans; never the name, note or comment text. Notes follow: ulid, step, market ulid, body **length**, never the body. New `AuditAction` cases are needed (plan 3.6).
- **Tenancy.** `BelongsToAgency` global scope on every model (new models included); routes under `auth:web`, `tenancy.agency`, `tenancy`; `findWave` resolves the wave inside the agency and brand; `WaveStrategyPolicy` allows any agency role to view, create, update and delete (`deleteInUse` is admin and manager); an unknown or cross-agency ulid is a 404. A client or creator user has no agency role: `CurrentAgencyRole::for($user)` is null, so every policy refuses.

## 7. Facts the plan depends on (one place)

1. No PL migration is on `main`: `git ls-tree origin/main` has no wave file; `origin/main` is `09169b5a` (fetched for this inventory).
2. `wave_markets` has `unique (wave_id, id)` (`unique_wave_markets_wave_id_id`): the parent key a composite foreign key can point at, as `wave_matrix_cells` and the concept tables do.

6. Grid widths today: USPs `minmax(min(100%, 290px), 1fr)`, personas `340px`, concepts `420px`, matrix columns `280px`.
