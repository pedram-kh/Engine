# AH-104 — Creator PII map (what erasure touches, table by table)

**Status:** PROPOSED. Awaiting Pedram's approval. No plan, no code. This is the contract the AH-104a erasure engine will be built
and tested against.
**Date:** 2026-10-20. **Precedes:** the AH-104a plan. **Builds on:** [`account-deletion-inventory.md`](account-deletion-inventory.md)
§5 (which this supersedes where they differ; the differences are called out in §7).
**Risk:** HIGH (irreversible, touches production personal data). **PROD-DATA RISK: HIGH** for the eventual command; this document changes nothing.

## 0. How to read this

**Scope.** 57 tables, taken from the 82 migrations in `apps/api/database/migrations` (schema dump reproduced by script, not by hand). Every
table appears in exactly one section of §3, including the ones with nothing to do (so "not in the map" can never mean "not looked at").
Columns are named wherever a table holds or references creator personal data; a table with no creator data is listed once with the reason.

**Subject.** "The creator" is a pair: the `users` row (`type = creator`) and its `creators` row. The erasure command resolves, **before it
changes anything**, a _subject set_: `user_id`, `creator_id`, the **old email** (needed to find rows keyed by the address, §4), the ids of the creator's
assignments, applications, relationship threads, agency relations, tax profile, payout methods, KYC rows, and the vendor ids on those rows
(`provider_account_id`, `provider_session_id`, `signature_envelope_id`). Every disposition below is stated against that set.

**Dispositions** (the vocabulary the user asked for, plus two the data forced):

| Code           | Meaning                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------- |
| **ANON**       | Row stays. Listed columns are overwritten (nulled, or replaced with a fixed non-display sentinel where `NOT NULL`). |
| **ERASE-ROW**  | Row is deleted. Only for rows the creator alone owns and no other party holds a claim on. **See decision D-A.**     |
| **KEEP**       | Row and column untouched. A reason is given, and it goes in the privacy notice.                                     |
| **SCRUB-JSON** | Row stays; named keys inside a JSON/text column are removed or nulled. Selection predicate given in §4.             |
| **DEL-MATCH**  | Transient or ledger rows deleted because their _content_ matches the subject (an address in a payload), not by FK.  |
| **EXPIRE**     | Nothing to do: the row has a TTL or no personal content. Stated so it is a decision, not an omission.               |
| **N/A**        | No creator data in this table (a creator can never be a row in it, or it holds only other parties' data).           |

**Marker.** "Anonymise in place with an explicit marker column" (ruling): `erased_at` on `users` and on `creators` (additive, schema-only
migration; any backfill is a separate command). `users.erased_at` is the login block and the exclusion predicate for every fan-out;
`creators.erased_at` is what agency resources read to emit an `is_erased` flag (the SPA renders the translated "Deleted creator"). **No English
string is stored or emitted as a display name** (the 24-locale gate): `users.name` gets a non-display sentinel and no resource may render it.

## 2. Findings that shape the map (new since the inventory)

1. **Prospect users exist.** `BulkInviteService::findOrCreateInviteeUser` (`BulkInviteService.php:116-137`) creates a `users` row with
   **`name = email`**, a random password, no verification, plus a `creators` row, for a person who has never signed up. They have no app
   to delete from, so they erase only via an admin request. Consequence: `users.name` can literally be the email, so ANON must cover `name`
   even where the creator never typed one, and audit snapshots of that user contain the email under `name` as well as `email`.
2. **`LoginFailed` writes the typed email into audit metadata** (`WriteAuthAuditLog.php:76-90`; `metadata.email`), and it does so with
   **no actor** for `temporarily_locked` (`AuthService.php:314`, `user = null`). Those rows are not reachable by actor or subject. They
   are found by **value** (`metadata->>'email' = :old_email`). A scrub keyed only on ids would miss them.
3. **`ip` / `user_agent` on an audit row belong to the _actor_.** For rows where an agency member or admin acted on the creator, the ip
   is the agency member's, not the creator's. Scrubbing it would damage other parties' records for no gain. The scrub nulls `ip` and
   `user_agent` **only where the actor is the erased user** (or the row matched by email value).
4. **Creator audit snapshots are narrower than the user's.** `Creator::auditableAllowlist` (`Creator.php:305`) holds `display_name` as
   its only name-like field (bio and paths excluded by design); `CreatorTaxProfile` excludes all three encrypted PII columns
   (`CreatorTaxProfile.php:87`). `User::auditableAllowlist` (`User.php:145`) holds `email`, `name`, `last_name`, `last_login_ip`,
   `suspended_reason`. That fixes the scrub key list (§4.1).
5. **`NOT NULL` columns cannot be nulled.** `creator_tax_profiles.legal_name`, `tax_id`, `address`, `tax_id_country`; `creator_social_accounts.handle`,
   `profile_url`, `platform_user_id`; `creator_payout_methods.provider_account_id`; `users.email`, `name`, `password`. ANON on these means a
   fixed sentinel or (for `email`) a unique placeholder, **not** a migration to make them nullable. Husk treatment never needs a schema change.
6. **Persistent copies outside the domain tables:** `failed_jobs.payload` (queued mail carries the address, `DebouncedMessageMailer.php:98-102`
   queues `Mail::to($recipient->email)`), `tracked_jobs.result.failures[].email` (`BulkCreatorInvitationJob.php:83-86`),
   `integration_events.payload` (raw vendor payload, `InboundWebhookIngestor.php:96`), `password_reset_tokens.email`.
7. **The erasure writes audit rows of its own.** The request-time row will carry the creator's ip (it is their action), so it is scrubbed at
   erasure. The erasure-time rows (admin actor) must carry **no subject email or name**; the audit spec for AH-104a asserts that.

## 4. The JSON and text scrub specifications

### 4.1 `audit_logs` (needs D-B)

**Row selection** (union, all evaluated against the subject set before any anonymisation):

| #   | Predicate                                                                                                                                 | Why                                               |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| S1  | `actor_type = user AND actor_id = :user_id`                                                                                               | The creator's own actions (logins, 2FA, accepts). |
| S2  | `subject_type = User AND subject_id = :user_id`                                                                                           | What the system or an admin did to the user.      |

| S4  | `subject_type ∈ {CreatorTaxProfile, CreatorPayoutMethod, AgencyCreatorRelation, BrandCreatorBlacklist, …}` resolved to the creator's rows | Satellite rows carry their own audit trail.       |

**Column actions:**

| `impersonator_user_id`                                                                           | all                | **KEEP** (an admin)                                                                                                                                        |

**Mechanics (for the plan, stated so the map is testable):** raw query builder, never the model; column-level grant (D-B); dry-run prints counts per predicate;
idempotent (re-running changes nothing); the command refuses without a subject set; one audit row per run, carrying counts and **no subject PII**.

**Stop writing the PII in the first place (separate, small, recommended):** drop `email`, `name`, `last_name`, `last_login_ip` from
`User::auditableAllowlist` and stop writing `metadata.email` on login failure for known users. That shrinks the scrub's surface for every
future user. It is a **behaviour change to audit content**, so it is its own stop-gate, not a rider on AH-104a.

### 4.3 `tracked_jobs.result`, `failed_jobs`, `integration_events.payload`

- `tracked_jobs.result.failures[].email` → remove entries (or null `email`) where `email = :old_email`. Predicate by value; there is no FK.
- `failed_jobs` → delete rows whose `payload` or `exception` contains `:old_email` (a `LIKE`, parameterised; dry-run prints the count first).
- `integration_events.payload` → replace the payload with `{"erased": true}` for events whose body contains any subject vendor id (account id, KYC session or
  decision id, envelope id). `processed_at` and the idempotency key stay, so a vendor retry is still recognised as a duplicate.
