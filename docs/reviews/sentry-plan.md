### B4. Release naming that survives the SHA rewrite

- **Rule: name a release by content, not by commit.** `release = <surface>@<tree-hash12>` where the tree hash is `git rev-parse --short=12 HEAD:apps/api` for the API; for main, the first 12 characters of `sha1(<HEAD:apps/main tree> + <HEAD:packages tree>)`; likewise for admin with `apps/admin`. Tree hashes are identical on GitHub, on the Bitbucket mirror, on the box and on Pedram's Mac for the same content, which is what the runbooks already rely on (`deploy-ah116-ah119.md:171-194`). Examples: `catalyst-api@3fa91c0d22b1`, `catalyst-main@8be0471c9a05`.
- **The phone uses the native form** (`com.catalystgrowth.platform@1.0.0+6`, B3) because native symbolication keys on it; its JS maps are uploaded under that same name.
- **Per surface, given the reported facts (R3):**
  - **SPAs:** Netlify builds both from the Bitbucket mirror **with git history**, so the helper in `vite.config.ts` reads git at build time and derives the tree-hash release; **`SENTRY_RELEASE` is only an override**, not a required variable. The same value is used for the runtime `release` and the map upload.
  - **API:** `/app` on the box is a bind mount of the git checkout, so the deploy step computes `git rev-parse --short=12 HEAD:apps/api` on the box and writes `SENTRY_RELEASE` into `.env` (one added line in the deploy runbook; `config:cache` afterwards). A bind mount means the checkout the operator pulled is the code that runs, so the hash describes what is live.
  - **Phone:** built on Pedram's Mac from his GitHub clone; the native-form name above.
- **Failure modes, named:** no `.git` in a build context (should not happen on Netlify, reported) falls back to `SENTRY_RELEASE`; if both are missing the build produces **no release** and prints a loud warning rather than failing the build or inventing a name (events still arrive; maps cannot match). A dirty tree appends `-dirty`. A docs-only change does not change the hash (`docs/` is outside these trees).
- **Cross-reference in the deploy-log entry:** one line `release names: api …, main …, admin …` next to the tree hashes the runbook already records (P1.1), so a Sentry release traces to a GitHub commit through the tree.

**Why the options did not reach native (source read: `@sentry/capacitor` 4.5.0 and sentry-cocoa 9.28.0).** The JS `FilterNativeOptions` is an allow-list and does not include `enableAutoSessionTracking` (so the `false` set in `sentryNative.ts` never left JS; the plugin even defaults it to true); the Swift `createOptions` reads only a fixed subset and reads none of `enableNetworkBreadcrumbs`, `enableNetworkTracking`, `enableAutoBreadcrumbTracking`, `enableMetrics` or the replay options; the plugin has no `autoInitializeNativeSdk`. Replay's `sessionSampleRate` and `onErrorSampleRate` default to 0 and the integration does not start recording when `onErrorSampleRate == 0` (`SentrySessionReplayIntegration.swift:202`), so it is listed but inert. Metrics only sends what the app emits through the metrics API (none is called).
