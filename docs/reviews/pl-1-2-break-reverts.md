## E1 (Erasure decisions)

The plan listed E1 as a gate. Two things were found:

- The new columns (`campaign_type`, `stage_key`) and the `campaign_type` audit key: removing their Erasure decisions did NOT turn anything red (three attempts). The verifier does not require a decision for these. The entries were kept anyway. This part is not a gate.
- The P3 `campaign.created` audit in `WaveService` carries literal keys the guard does read. The first run of the Erasure folder was RED on five undecided keys (`budget_currency`, `budget_minor_units`, `creator_posts_content`, `listed_on_jobs_board`, `objective`). They were decided in `AuditPayloadKeys::notPersonalKeys()`, and the folder is green (337 passed). That is a real gate: break-revert `E1-audit-keys` in the table below.

## Notes

- L4 cannot go red on SQLite (it ignores row locks), so it runs on PostgreSQL and is skipped on SQLite. CI runs PostgreSQL, so it runs there.
- The P3 `Gate::authorize('create', Campaign::class)` in `WaveController::store` has no break-revert. Admin and manager hold both abilities and staff are refused earlier by the wave policy, so the line cannot be reached with a role that lacks it. It is defence in depth, not a gate.
- Every gate was run on the real code first, then broken, then reverted.
- The comment-node counts in the W2 specs (219 form, 95 campaign page, 55 normal board) were measured on the pre-PL-1.2 code at `a173a9b2` with the same props, then pinned. Counts are large because Vuetify draws its own anchors; what is pinned is that PL-1.2 adds none.
- The web break-reverts were run by one script that breaks, runs the spec, restores the file and prints the result (`git diff` was checked clean of the break afterwards).
