# PL-1.2 inventory: Campaign for a wave

**Date:** 2026-11-17. **Branch:** `pl`, from tip `55538abd`. **Scope:** read-only. No code, no migration, no push.
**Rulings in force:** R1 to R10 (`production-line-sprints.md` §6) and P1 to P9 (Pedram, 2026-11-17, recorded in `pl-1-2-plan.md` and `production-line-sprints.md` §6).

Paths are relative to the repo root. `api` = `apps/api/app/Modules`, `web` = `apps/main/src/modules`.

## Headline findings (they shape the plan)

1. **The board is per campaign, in the data, and a card IS an assignment.** `boards` (one per campaign), `board_columns` (per board, agency-editable), `board_cards.assignment_id` NOT NULL, UNIQUE, CASCADE. A card exists only once a creator is **invited**. An application has no card.
2. **The "Applied" column already exists as a pseudo-column.** `web/boards/components/BoardApplicationsColumn.vue` renders pending applications at the left of the board. It is not in the data on purpose (`board_cards.assignment_id` is NOT NULL). It has no drag in, no drag out, and uses the same Accept and Reject dialogs as the Applications tab.
3. **A non-posting campaign already exists.** `campaigns.creator_posts_content` (boolean, default true, migration `2026_08_16_100000`, AH-069) already changes the board (hides the Posted column at render), the invite (`posting_due_at` null), the state machine (ends at approval) and the creator draft endpoint. P1's "creator does not post content" can reuse it instead of inventing a second mechanism.
4. **"Selected" has two existing meanings and neither is P6's.** `AssignmentStatus::countsAsSelected()` is true from **Accepted** onward (used by brand exclusivity). P6 says an Accepted card stays in Invited **until the strategist selects**. So P5's lock cannot read assignment status; it has to read the board.
5. **The creator app is the same SPA (`apps/main`) bundled by Capacitor (`webDir: dist`).** Nothing in this chunk needs a creator-visible change. Details in section 5.
6. **The Erasure registry decides every string column.** A new string column on `campaigns` and on `board_columns` needs a registry entry (section 6).

### How columns are defined and stored

- **Per campaign, never global.** `api/Boards/Support/BoardDefaults.php` is the single source for the **default seven**: To Define, Invited, In Review, Approved, Posted, Paid, Cancelled / Rejected. The ten default automations are in the same file.
- `api/Boards/Services/BoardProvisioningService.php::provisionDefaults()` seeds columns **only when the board has none** and `firstOrCreate`s automations on `(board_id, event_key)`. It reads `BoardDefaults` directly, with **no input from the campaign**, so today it cannot seed a different shape.
- `api/Boards/Services/BoardService.php::ensureBoard()` creates the board lazily (first invite, first GET) and provisions defaults when `wasRecentlyCreated`. `forCampaign()` also heals any assignment that lacks a card.
- `api/Boards/Services/BoardResetService.php` (route `POST …/board/reset-to-defaults`) deletes and re-seeds the **default seven**. On a for-a-wave board this would destroy the nine columns, so it must become type-aware.
- Column CRUD (`BoardColumnController`, `BoardColumnService`): create, rename, recolour, reorder, delete with a destination. Admin and manager. Automation config (`BoardAutomationController`): admin and manager.
- Terminal columns: at most one success and one failure column per board (`BoardColumnService::enforceTerminalUniqueness`).

### How a card is created and moved

- **Created** by `api/Boards/Listeners/CreateBoardCard.php`, a consumer of `AssignmentTransitioned`, **only when the action is `AssignmentInvited`**. `BoardCardService::forAssignment()` is a `firstOrCreate` on `assignment_id`; the first column comes from `resolveColumnForState()` (the automation for the assignment's state, else the Invited automation, else the first column).
- **Automatic moves:** `BoardAutomationListener` → `BoardAutomationService::processEvent()` on every assignment event. The ten defaults move a card on: invited, draft submitted, draft approved, posted by creator, live verified, manually verified, resubmit requested, payment released, cancelled, draft rejected. **Accepted and Declined have no automation**, so an Accepted or Declined card **already stays in its column** (Invited). `Declined` is not routed to Cancelled / Rejected. P6's Invited / Accepted / Declined rule is therefore already the behaviour; only the label is missing.
- **Manual move:** `POST agencies/{agency}/campaigns/{campaign}/board/cards/{card}/move` (`api/Boards/Http/Controllers/BoardCardController.php::move`), gated on the `invite` ability (**admin, manager and staff**). `BoardCardMoveService::move()` writes the card, a `board_card_movements` row (trigger `user`) and one audit row `board.card_moved_manually`, in one transaction. **No other rule**: any column on the board, any direction.
- **Drag and drop:** `web/boards/components/BoardColumns.vue` and `BoardColumn.vue` use `vuedraggable`, with `group="board-cards"` for cards and a separate `board-columns` group for column reorder (admin and manager, `canEditColumns`). `BoardApplicationsColumn.vue` is deliberately outside both groups ("enforced by absence").
- **Poll:** `web/boards/composables/useBoardPoll.ts`. Store: `web/boards/stores/useBoardStore.ts`. Card face: `BoardCard.vue`; drawer: `BoardCardDrawer.vue` (786 lines).

`BoardCardMoveService` and the board automations touch only `board_cards`, `board_card_movements` and the audit log. The comment in `BoardAutomationService.php` says it explicitly: the board is **not** a consumer of notifications, system messages or message threads. No notification, no push, no creator status, no creator-app screen reads a board column. **A hand move changes nothing a creator can see.**

## 3. "Selected" today, and what P5's lock should read

- `api/Campaigns/Enums/AssignmentStatus.php::countsAsSelected()` is **true from Accepted** (Accepted, Contracted, Producing, DraftSubmitted, … PaymentReleased, CompletedOnApproval). `isPreSelection()` is Invited and Countered. The only consumers are `Services/BrandExclusivity.php` and the enum itself. This is the AH-120 "selected on a blocking campaign" idea.
- **P6 contradicts it by design:** an Accepted creator stays in Invited until the strategist moves the card to Selected. So "Selected" in PL-1.2 is a **board position**, not an assignment status.
- **There is nothing stored today that says "the strategist selected this creator".** The lock must read the board. **Ruled (Q3, 2026-11-17): current card positions only**, not movement history: locked while at least one card is in Selected, Filming, Submitted / in review, In edits, Client review or Approved.
- **Problem:** columns have no stable identity (names are editable). The plan adds a nullable `board_columns.stage_key` set only on for-a-wave boards, and fixes the wave board's columns (no rename, delete, reorder). `board_card_movements` is **not** read by the lock (Q3).
- The **assignment is not touched** by the move to Selected in this chunk (no hand-off, no contract; R7 says hand-off is a later sprint).

## 6. Erasure, audit and tenancy touchpoints

**Audit actions:** `campaign.created` and `campaign.updated` (`AuditAction.php:268-269`), `wave.created`, `wave.updated`, `board.card_moved_manually` (`:429`). No new action is required. The P3 transaction writes `campaign.created` and `wave.created`.

**Tenancy:** all routes sit under `auth:web`, `tenancy.agency`, `tenancy`. Boards controllers re-assert the campaign's agency (`assertCampaignBelongsToAgency`). ## 8. Gaps closed (2026-11-17)

**G1: zero budget and publishing.** `CreateCampaignRequest` and `UpdateCampaignRequest` accept `budget_minor_units` with `min:0`; currency must be 3 letters. There is **no publish action**: `status` is a free `sometimes` enum field on update (Draft, Active, Paused, Completed, Cancelled) and `published_at` is only set by the factory. The jobs-board listing floor (`ValidatesJobsBoardListing::LISTING_FLOOR_FIELDS`: description, listing duration, fee, languages, regions) **does not include budget**. The budget amount is read nowhere else: offers and counters check only that the fee currency equals `budget_currency`, and the offer is explicitly not constrained to the amount. **So a zero-budget campaign can be saved as draft, set Active and listed, with no refusal.** The plan adds a guard for for-a-wave campaigns only (`campaign.wave_budget_required`, plan §3.1, gate WB1). Normal campaigns are unchanged.

**G2: board code.** `BoardAutomationService` moves a card only for an event with an enabled automation and a target; a wave board has two (invited, cancelled). `OverdueScanService` posting scan is limited to `creator_posts_content = true` (a wave campaign is false); the draft scan can still flag the assignment but fires an event with no automation on a wave board, so **no card is moved**. `BoardResetService::reset` deletes every column and re-seeds the default seven, which **would destroy a wave board**; the plan refuses it twice (controller and service). The existing board already has columns side by side, a name and count chip per column, drag between columns with optimistic move and revert, a horizontal scroller and click-to-open detail. Missing: the nine-column data, a slimmer card face (no fee, due date), the invite label, a specific refusal message and hidden structure controls. Plan §4.4 and §4.5.

**G3: what the creator sees.** `apply` (`CreatorJobBoardController::apply`) creates a pending `CampaignApplication` and returns status, note and created_at. `CreatorJobCardResource` and `CreatorJobDetailResource` emit an explicit key list (name, status, listing fee and duration, applicant count, brand, description, languages, regions, attachments, locks) from an explicit column select (`CARD_COLUMNS`): **no budget, no campaign type, no wave**. A for-a-wave campaign therefore shows the creator nothing about waves. **About posting:** the list and detail say nothing, but the creator's assignment draft response (`CreatorAssignmentDraftController`, meta `creator_posts_content`) is false for a wave campaign, so the creator's assignment page hides the "post" form after approval and the server answers `assignment.posting_not_required`. That is existing AH-069 behaviour, not wave-specific. The description is agency free text and could say anything. Gate CR1.

**G4: PL-1.1 tests and seeder.** Read line by line; exact changes are in plan §6 ("PL-1.1 tests that change"). Three backend test files, the fixtures and the factory, the Pl11 seeder, and three web files change; seven others were read and are unchanged.
