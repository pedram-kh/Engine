## 3. Upload code to reuse (PL-1.1 brand files)

Read: `BrandFileUploadService`, `BrandFileController`, `AttachmentMimeTypes`, the web `BrandFileUploadDialog`, `brandFiles.api.ts`, `uploadToPresignedUrl` (imported from `@catalyst/api-client`), the brand file routes and the `brand_files` registry rule.

### 3.1 What the flow does

1. `POST …/files/uploads/init` validates MIME (against a map), declared size (1 byte to 100 MB) and builds a key `agencies/{agency_ulid}/brands/{brand_ulid}/files/{ulid}.{ext}`. The extension comes from the **declared** MIME. On S3 it returns a presigned PUT signed with `ContentType` and `ContentLength` (15 minutes); on a local disk it returns a `/_test/presigned-upload/…` URL.
2. The browser PUTs the file to that URL (`uploadToPresignedUrl`).
3. `POST …/uploads/complete` checks the key starts with this brand's prefix, that the object exists, derives the MIME **from the key's extension**, reads the size from the disk, refuses an empty or over-cap object, and inserts a row. `storage_key` is unique, so a second `complete` for the same upload is refused (no second row, object left alone).
4. Download: `signedDownloadUrl` gives a presigned GET (60 minutes, `Content-Disposition: attachment`), carried in the list resource. `storage_key` is never exposed.
5. Delete is **object-first** (`StorageDeleteFailedException` unless the delete is confirmed), then a soft delete of the row.

### 3.2 Differences from what C4 asks

### 3.3 Thumbnails: what exists

`composer.json` has `intervention/image` ^4 and the PHP build has `gd` and `exif`. `PortfolioImageProcessor` (Creators module) is the precedent: it guards against decompression bombs **before** decoding with `getimagesizefromstring` (header only, `MAX_MEGAPIXELS = 50`), produces a separate thumbnail (`THUMBNAIL_MAX_EDGE = 512`), and marks the item failed instead of downscaling silently. It runs in a queued job there. A concept image would reuse its guard and thumbnail size (not its re-encode of the original: references are kept as uploaded; plan §1.5). GD decodes the whole file into memory, so the memory ceiling of the worker is the real limit on one image; with no per-image cap (C4) a very large file fails to thumbnail and shows the placeholder tile of the frame (Q9).

### 3.4 Web side

`BrandFileUploadDialog.vue` takes `multiple` files and PUTs each with `uploadToPresignedUrl`; the client side runs uploads as the browser allows, so **several `init` calls can arrive at once**. That is why the total cap has to be a server-side reservation and not a check at `complete`.

## 5. Erasure, audit, tenancy

### 5.1 Tenancy

Every strategy table has `agency_id` (FK `agencies`, RESTRICT) and the model uses `BelongsToAgency`; routes live under `agencies/{agency}/brands/{brand}/waves/{wave}/strategy` and look rows up by ulid scoped to agency and wave (another agency's row is a 404, never a 403). The PL-2.2 composite FKs are the model: `(wave_id, market, persona_id)` to `wave_personas (wave_id, market, id)` (unique index exists) and `(wave_id, usp_id)` to `wave_usps (wave_id, id)` (unique index exists). The new tables reuse both indexes and add their own `(wave_id, market, id)` unique on `wave_concepts` as the parent key of every child, so a chip, image, link or decision cannot cross a wave or a market at the database (plan §1.2).

### 5.2 Audit

`Audit::log(action:, actor:, subject:, metadata:, agencyId:)` with the `AuditAction` enum; every literal payload key must be decided in `AuditPayloadKeys` (scrub, kept or not personal) or `AuditPayloadKeysGuardTest` fails, and the action must be in the `AuditActionEnumTest` catalogue. The PL-2.1/2.2 precedent writes ulids, market, colour and counts and **never titles or text**. New actions and their keys are in plan §3.6. Two traps found in the registry: `note` is already a **kept** key (a KYC decision note) and `name` is a **scrub** key, so concept payloads use `has_note`, `has_comment` (booleans) and never `name`, `note` or `comment`.

### 5.3 Erasure registry

`ErasureRegistry` has one `TableRule` per table. `refs` lists the exact FK columns to `users` or `creators`; the verifier fails when a new FK is not declared or a PII-shaped column is not classified. Precedent: `wave_personas`, `wave_usps`, `wave_matrix_cells` are `NotApplicable` ("Agency-authored (§3.7)"), `refs` empty, `classified` carries one reason per free-text column; `brand_files` is `NotApplicable` with `refs ['uploaded_by_user_id']`.

For PL-2.3: `wave_concepts` and the chips, images and links tables are `NotApplicable`, "Agency-authored (§3.7)". The images and decisions tables declare `uploaded_by_user_id` and `recorded_by_user_id` as `refs` (nullable, `nullOnDelete`, as `brand_files` and `wave_steps.owner_user_id`).

**The client's name and comment (`wave_concept_decisions.client_name`, `comment`, `note`).** They are typed by agency staff about a **client contact**, a real, named third party ("Anna K."), not a creator and not a user of the platform. The existing precedent for free text that may name a person is PL-2.1 plan §3.7 ("why an invented persona name is not personal data"): a creator erasure never reaches an agency-authored table because no column points at a creator, the agency is the controller of the text, and the agency can edit or delete it. That precedent does **not** fit as it stands, because here the field is _meant_ to hold a real person's name. The closest existing classification is the agency's billing contact (`'billing_email' => 'The agency's billing contact'`, registry line 303), a third-party contact kept and classified, never erased by a creator flow. Recommendation (Q10): `NotApplicable` for the table, with `client_name`, `comment` and `note` each **classified** as "typed by agency staff about a client contact (a third party, not a creator or user); kept; leaves with the concept when the agency deletes it", plus a sentence in the privacy and sub-processor documents that client contacts' names appear in strategy decisions. No erasure flow exists for client contacts and none is built here.

With `strategy_enabled` OFF the strategy entry and every route are absent for both walks, so nothing in the baselines moves.
