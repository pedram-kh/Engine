# PL-2.3 Stage 1: break-revert record

Method, for every gate: patch the code (or the registry or migration the gate protects), run the targeted tests and
require them **red**, restore the file from memory, re-run the same tests and require them **green**. The driver restores
each file in a `finally`; `git status` after the run showed no source change besides the tests edited on purpose.
87 gates, 87 red under the break, 87 green after the revert. Lock and schema gates ran on PostgreSQL
(`catalyst_test`, port 5435, `phpunit.pgsql.xml`); the others on SQLite.

## Gates the first pass found weak (fixed, then re-run red)

| Gate                           | What the first pass showed                                                                                            | Fix                                                                                                                                         |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| C13 duplicate starts Awaiting  | The test approved the source, then added a link, which (Q6) sent the source back to Awaiting; the break was invisible | Test now decides after the link, so the source is Approved at duplicate time                                                                |
| D1 client name required        | HTTP validation `required` catches it first; the service check is a second line the HTTP tests cannot reach           | Gate breaks both lines; the service check stays as defence in depth, not separately tested                                                  |
| I14 pixel and side thresholds  | A header-only bomb has no body, so the decoder fails soft anyway and the test stayed green without the threshold      | Test now spies on the log: a decode error logs a warning, a threshold refusal does not; the over-threshold cases must not reach the decoder |
| I21 sweeper filters on pending | No ready row older than the cutoff existed in the test                                                                | The ready row now carries an expiry 3 h in the past                                                                                         |

## Migration rehearsal (G4)

Throwaway PostgreSQL database `catalyst_rehearsal` (container `catalyst-postgres`, port 5435); `select current_database()` printed first. Never `catalyst`. The database held the full schema up to PL-2.2 plus the PL-2.2 walk seed.

| Table               | Rows before  | Rows after |
| ------------------- | ------------ | ---------- |
| agencies            | 2            | 2          |
| users               | 4            | 4          |
| waves               | 4            | 4          |
| wave_personas       | 13           | 13         |
| wave_usps           | 11           | 11         |
| the five new tables | do not exist | 0          |

`artisan migrate` ran the five migrations in 0.24 s in total: 20.4, 10.3, 15.5, 9.3 and 12.2 ms. `down()` ran clean in reverse (`migrate:rollback --step=5`). The data scale is tiny (a walk seed), so the timing proves the shape, not production volume; the migrations create empty tables, so existing row counts do not enter the cost.

Locks, read from `pg_locks` for the migrating backend inside each migration's transaction, with `lock_timeout` = 5 s confirmed in effect:

| Migration                     | New table                                  | Locks on EXISTING tables (the foreign keys)                      |
| ----------------------------- | ------------------------------------------ | ---------------------------------------------------------------- |
| 200001 wave_concepts          | AccessExclusive (new, invisible to others) | `ShareRowExclusive` on agencies, waves, wave_personas            |
| 200002 wave_concept_usps      | same                                       | `ShareRowExclusive` on agencies, waves, wave_concepts, wave_usps |
| 200003 wave_concept_images    | same                                       | `ShareRowExclusive` on agencies, users, waves, wave_concepts     |
| 200004 wave_concept_links     | same                                       | `ShareRowExclusive` on agencies, waves, wave_concepts            |
| 200005 wave_concept_decisions | same                                       | `ShareRowExclusive` on agencies, users, waves, wave_concepts     |

What this means: adding a foreign key takes `SHARE ROW EXCLUSIVE` on the referenced table, which blocks writes (not reads) to `agencies`, `users`, `waves`, `wave_personas` and `wave_usps` for the milliseconds the migration runs. It never takes `ACCESS EXCLUSIVE` on an existing table, and it writes no data. The 5 s `lock_timeout` makes a migration fail fast rather than queue behind a long transaction and stall writers. No existing table is altered.
