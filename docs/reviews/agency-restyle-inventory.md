## 0. Summary for the reviewer

1. **The gating answer (§1).** Theme and tokens are **shared** between the agency shell and the creator shell on web. They live in one global Vuetify theme (`light` / `dark`) and one global `:root` stylesheet. The creator _native_ app additionally swaps in its own dark theme and a `.catalyst-native` stylesheet. So the new tokens must **not** be written into any shared theme key or into `:root`. The cheapest safe scope is **two new Vuetify themes registered for the agency shell only (`agency-dark`, `agency-light`), applied with `<v-app :theme>` in `AgencyLayout.vue`, plus one agency-only stylesheet whose selectors all start with those theme classes.** That leaves `light`, `dark`, `nativeDarkTheme`, `tokens.css` and `native.css` byte-identical.
2. **The agency shell can never render inside the native app (READ).** Native sign-in is creator-only, and the native build bundles its own `dist`. So a web deploy of agency-only code cannot reach build 3 even by accident. The real risk is the **web creator app**, which shares 21 `.vue` files with the agency (§7).
3. **The new palette is mostly not new to the repo.** 19 of the 26 Figma colour tokens already exist as `nativePalette` in `packages/design-tokens/src/native.ts:24-45` (including `bg-sidebar` and `bg-topbar`), so the agency theme can import that object. The seven with no repo value are `status-neutral`, `status-ai`, `usp-1` to `usp-4` and `highlight-message-line` (§2.1); none of the seven is needed by an agency screen except possibly `status-neutral`.
4. **The ruling "dark becomes the agency default" is already true.** `defaultTheme: 'dark'` (`apps/main/src/plugins/vuetify.ts:47`) and `SPA_DEFAULT = 'dark'` (`apps/main/src/composables/useThemePreference.ts:68`). What changes is the _values_ of dark, not which theme is the default. See §8 Q2.
5. **A latent bug that decides whether agency light is even reachable (§1.6, §8 Q3).** The stored theme preference is applied only when `ThemeToggle` mounts, and `ThemeToggle` lives inside the lazy user menu. A user with a stored `light` preference most likely sees dark at load until they open the menu. Read statically; not reproduced.
6. **Figma has inconsistencies we must resolve, not inherit (§8):** sidebar 300 / top bar 68 on the Patterns page versus 280 / 65 measured in all the frames; the Foundations page says "dark only" but the ruling is both themes; `radius/xl` is 10 in Figma versus 12 in the web repo.
7. **The design shows things the app has no data for** (status counts on Campaigns, "Budget used", "Next steps", Discover gender and "has portfolio" filters, the market count, per-card video counts, Messages brand and "wave" filters and online presence). "Wave" is not a word in this product (§4). Each is a stop-gate trigger if built. Two things the design shows already have a data source: the filtered result total (`meta.total`, `packages/api-client/src/types/agency.ts:593-600`) and, per a code comment, a backend age filter on the discovery endpoint (`age_min` / `age_max`, comment at `agency.ts:358-371`; the client type `DiscoveryListParams`, `:603-611`, does not carry them yet, so using it needs a client-type addition).
8. **Typography is the largest hidden cost.** The agency pages use Vuetify's global `text-*` classes 225 times (§2.3). Those classes are `!important` and global, so the type re-map needs scoped `!important` overrides, not a token edit.

### 1.3 Why a native build cannot be affected by an agency-only web change (READ)

- The native app bundles its own build: `webDir: 'dist'`, no `server.url` (`apps/main/capacitor.config.ts:16`). A web deploy changes `dist` on the server, not the binary in TestFlight.
- Native login is the creator-only token door (`apps/api/app/Modules/Identity/Http/Controllers/TokenLoginController.php:16`, "the creator app's login"). An agency user cannot authenticate natively, so `AgencyLayout` never mounts there.
- Even so, the brief says creator web must render byte-identically, and that is a stricter bar than "native unaffected". The plan below is designed for the stricter bar.

**C1 — register in `buildVuetifyOptions(false)`.** Simple, but the web options object changes, so the pin `expect(buildVuetifyOptions(false)).toStrictEqual(WEB_CONFIG_AT_D1AB5820)` (`apps/main/tests/unit/plugins/vuetify.spec.ts:45`) must be rewritten. That edit weakens the one spec whose job is "the web config does not change", so I do not recommend it.

**C2 — register at runtime from an agency-only module (recommended).** `AgencyLayout` (or a module it imports) calls `vuetify.theme.themes.value['agency-dark'] = ...` once. `buildVuetifyOptions(false)` and `(true)` stay exactly as pinned, so `vuetify.spec.ts` passes **unmodified**. Vuetify's theme styles are a reactive `computed` over `themes`, so a runtime registration regenerates the stylesheet. (READ in `vuetify@3.12.5/lib/composables/theme.js:227-262`: per-theme `.v-theme--<name>` rules are generated for every key in `computedThemes`, and the `styles` computed is what gets written to the head.) `UNVERIFIED` in a browser: confirm the runtime registration produces the rules before first paint (a flash of the global theme would be the symptom). That is the first thing to prove in a spike.

**Selector scoping rule (important, `INFERRED` from the Vuetify source).** Vuetify teleports menus, dialogs and tooltips to a container outside the layout. A plain class on the layout root would miss them. Vuetify copies the active _theme class_ onto those overlays, so the agency stylesheet must be scoped to the **theme classes** (`:is(.v-theme--agency-dark, .v-theme--agency-light)`), not to a custom class on `AgencyLayout`. This also gives a clean architecture pin: every selector in `agency.css` starts with those two classes (same shape as `native-css-scoping.spec.ts:35-37`).

**Agency-scoped component defaults.** `defaults.VBtn` is global. To give agency buttons 8px radius and the Md 40 / Sm 32 heights without touching the global defaults, wrap the agency tree in Vuetify's `<v-defaults-provider>` (agency-only) or do it in `agency.css`. `INFERRED`, not tried.

**Variables the agency stylesheet may redefine, because they are read through `var()` by shared code (INFERRED).** `--radius-*` is read by `defaults.VBtn` (`vuetify.ts:62`) and `--catalyst-typography-*` by the `@catalyst/ui` components (pinned by `typography-consumption.spec.ts`). Redefining them _inside the agency theme-class scope_ restyles the shared `@catalyst/ui` components in the agency without editing them. That is the cheapest way to avoid touching shared files.

### 1.6 Latent finding: a stored `light` preference is probably not applied at load (READ, not reproduced)

- `useThemePreference()` is what applies the stored value to Vuetify (`useThemePreference.ts:165-175`). Its header says it "runs from `App.vue`'s setup()" (`:48-51`).
- The only non-test caller in `apps/main/src` is `ThemeToggle.vue:45`. `App.vue` and `main.ts` do not reference it (searched).
- `ThemeToggle` is rendered inside the user `v-menu` in `AgencyLayout.vue:148-178` and `CreatorDashboardLayout.vue:297-328`. Vuetify overlay content is lazy, so it mounts the first time the menu opens.
- `App.vue:17-19` records that `ThemeToggle` was moved out of the bare `v-app` into the layouts' menus in "Chunk 2", which is the probable moment the bootstrap stopped running at startup.
- Consequence: a user with a stored `light` preference most likely loads in dark and flips to light only after opening the user menu. Agency light mode is therefore much less visible than the ruling assumes. **How to confirm:** set `localStorage['catalyst.main.theme']='light'`, hard reload, read `document.querySelector('.v-application').className` before opening the menu.
- It also decides how the agency picks `agency-dark` versus `agency-light`: the layout must read the stored preference itself. The fix cannot go in `App.vue` (shared; it would change creator web). See §8 Q3.

### 7.3 New specs this chunk should add (proposals, in the repo's break-revert style)

1. **`agency-theme-scoping.spec.ts`:** every selector in the agency stylesheet begins with `.v-theme--agency-dark` or `.v-theme--agency-light` (copy the parse in `native-css-scoping.spec.ts`); no `:root`, `html`, `body` selector; no literal colour needed outside the sheet.
2. **`agency-theme-isolation.spec.ts` (import-graph):** nothing reachable from the creator, onboarding or auth route tables imports the agency stylesheet or the agency theme module. This is the byte-identical guarantee in executable form; the `/tmp` script is the starting point.
3. **`shared-tokens-frozen.spec.ts`:** a frozen literal copy of `lightTheme`, `darkTheme`, `nativeDarkTheme` and a hash of `tokens.css` and `native.css`, so an accidental edit to any shared token file fails.
4. **`color-system-parity` sibling for `agency-dark` / `agency-light`:** status and accent **fills** equal in both themes, neutrals differ, every `on-*` pair meets AA-normal (the §2.2 table gives the targets), the light `primary` is not the failing teal-500 / white pair.
5. **Shared-component polarity pins** for every one of the 21 files that the plan changes by prop or fork: with the agency prop off, the rendered DOM equals a frozen snapshot (the `*.native.spec.ts` "web polarity" style).
6. **`agency-status-tone.spec.ts`:** every status value in the §6.2 unions has a label key in all 24 locales and a tone, so a new backend status cannot ship as a bare coloured chip.
7. **A computed-style check for creator web:** mount a creator page under the real Vuetify with both themes and assert `.v-theme--agency-*` never appears in its tree (jsdom does not paint, so the pin is the class, not pixels).

**Disclosure about pixel proof.** The earlier audits disclosed that jsdom specs cannot prove rendering (`creator-app-fidelity-audit-review.md`, §8: "no rendered-pixel comparison"). The same limit applies here. "Byte-identical" for creator web is therefore proved by **file-level and DOM-level** pins plus a before / after screenshot walk of the creator pages, not by vitest alone. §8 Q14.

### 7.4 Other risks

- **Shared messaging components** are the single largest risk (the Messages restyle wants DOM changes in files the creator app renders). §8 Q9.
- **Light mode reachability** depends on the §1.6 finding.
- **Runtime theme registration** (C2) could flash the global theme before the agency theme exists. Spike item 1.
