## 1. Data model and rules

All tables are in the Strategy module, `BelongsToAgency`, factory, `ulid`, `agency_id` taken from the **locked wave**, never from the request. Every foreign key is `RESTRICT` except user columns (`nullOnDelete`).

### 1.1 Tables

**`wave_scripts`** (a): one script of one creator in one market.

| Column                                     | Type                        | Notes                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------ | --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`, `ulid`, timestamps                   | standard                    |                                                                                                                                                                                                                                                                                                                                                       |
| `agency_id`, `wave_id`                     | FKs                         |                                                                                                                                                                                                                                                                                                                                                       |
| `market_id`                                | bigint                      | composite FK `(wave_id, market_id)` to `wave_markets(wave_id, id)`                                                                                                                                                                                                                                                                                    |
| `creator_id`                               | FK `creators`, RESTRICT     | the creator row is anonymised in place and never deleted (inventory 5), so RESTRICT never blocks erasure                                                                                                                                                                                                                                              |
| `wave_creator_id`                          | bigint **nullable**         | composite FK `(wave_id, market_id, wave_creator_id, creator_id)` to `wave_creators(wave_id, market_id, id, creator_id)`: a script can only point at a slot of **its own wave, market and creator**; **`ON UPDATE CASCADE` on the creator column** so a carry-over on Replace moves the scripts with the slot (1.8). Null while the script is archived |

Keys: unique `(wave_id, market_id, id)` (child FK target); unique `(wave_id, creator_id, number)`; index `(wave_id, market_id, creator_id)`; index `agency_id`. **One more key on a PL table (migration M1):** unique `(wave_id, market_id, id, creator_id)` on `wave_creators`, the target of the four-column FK (a superset of its primary key, an empty table in production).

**`wave_script_hooks`** (a): `id`, `ulid`, timestamps, `agency_id`, `wave_id`, `script_id` (composite FK `(wave_id, script_id)` to `wave_scripts(wave_id, id)`), `position` smallint, `shot_type` varchar(24) (CHECK in the ten codes of 1.2), `visual_description` text (English only, at most 400), `revision` integer. Unique `(script_id, id)` for the children. **The hook letter is not stored**: it is derived from `position` (0 = A), so reorder, duplicate and delete never renumber a column. At least one hook is enforced in the service (the last hook cannot be deleted; a new script is created with A, B and C).

**`wave_script_hook_texts`** (a): `id`, `agency_id`, `wave_id`, `script_id`, `hook_id` (composite FK `(script_id, hook_id)`), `field` varchar(8) CHECK in (`audio`, `overlay`), `language` char(2), `body` text, `origin` varchar(8) default `manual` with CHECK `origin = 'manual'`, timestamps. Unique `(hook_id, field, language)`. **English is `language = 'en'`**; the local language is a second row. An empty overlay is no row.

**`wave_market_script_languages`** (b): `id`, `agency_id`, `wave_id`, `market_id` (composite FK to `wave_markets`), `language` char(2), `position`. Unique `(market_id, language)`. **English is not stored** (always present). CHECK `language <> 'en'`.

**`wave_script_lines`** (b): as hooks, plus `cta` boolean default false; **no stored number**: the line number is `position + 2` (the hook is line 1). **`wave_script_line_texts`** (b): as hook texts, `field` = `text` only. **`wave_script_broll`** (b): `id`, `ulid`, `agency_id`, `wave_id`, `script_id`, `line_id` (composite FK `(script_id, line_id)`), `position`, `shot_type`, `description` (English, at most 300). **The B-roll code is derived** (`{line}_{n}` from the line's position and the row's position, Q2), never stored.

**`wave_script_images`** (b): the shape of `wave_concept_images` (inventory 3): `ulid`, `agency_id`, `wave_id`, `script_id`, **`hook_id` and `line_id` both nullable with CHECK exactly one is set**, composite FKs `(script_id, hook_id)` and `(script_id, line_id)`, `position`, `storage_key` unique, `thumb_key` unique nullable, `original_filename`, `mime_type` CHECK in (`image/jpeg`, `image/png`, `image/webp`, `image/gif`), `declared_bytes`, `size_bytes`, `status` CHECK in (`pending`, `ready`), `expires_at`, `uploaded_by_user_id` (`nullOnDelete`). Indexes: `(script_id, status)`, `(hook_id, status)`, `(line_id, status)`, `expires_at`, `agency_id`.

**Why a text table per owner, with a `language` column:** a column per language is impossible (the list is data); one polymorphic table needs an exactly-one-owner CHECK and loses composite keys. Two small tables keep every key composite. The `language` column is there from PL-3.2a, so PL-3.2b adds languages to hooks with **no schema change**.

### 1.2 The shot type list (fixed)

Stored as codes: `wide`, `medium`, `close_up`, `detail`, `pov`, `over_the_shoulder`, `top_down`, `screen_recording`, `reaction`, `creator_to_camera`, shown as the ten labels of inventory 1.8 in that order. The list is **a PHP enum and a TS union with a parity test**; the CHECK is the enum's values. Adding a type later is one enum case and one CHECK migration.

### 1.3 What PL-9 and S3 need (E1, E2)

- **PL-9 additive.** Texts carry `origin` (`manual` only now; PL-9 widens the CHECK to add `ai` and adds a nullable `reviewed_at`). Generation writes the same rows a person writes. A regenerated block is a normal block save. Nothing in PL-3.2 reads `origin` except to show it later.
- **S3 (versions, PL-3.3) is not blocked.** The script is a tree of ordinary rows, so a numbered copy is a JSON snapshot of that tree; `revision` on the script gives "edited since"; image objects are copied server-side at send time (the concept duplicate already does `ConceptImageStorage::copy`), because the live script may later delete its own. Derived codes (hook letter, line number, B-roll code) are computed from the snapshot's order, so a frozen version keeps its own codes. **Nothing in the model overwrites history; no decision is attached to a mutable row.**

### 1.4 The brief: what is stored, what is read live, and what happens when the source changes (E4)

| Brief row | Stored on the script        | Read live                                                                                                                                  |
| --------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Persona   | **nothing**                 | the creator's slot `persona_id` (the matched persona: code, title, colour)                                                                 |
| USPs      | **nothing**                 | the persona's matrix cells with `level` priority and support (priority first), each USP's title; "low" and unset cells are not shown       |
| Angle     | `angle` (null until edited) | while null: the persona's angle line for the **first Priority USP** (`wave_persona_angles.explanation`), else the cell's `rationale` (Q15) |
| Duration  | `duration_seconds`          | the **estimate** (computed in the browser from the text on screen, never stored)                                                           |
| Link      | nothing                     | "Edit in step 3" opens the matrix at this market (existing route `strategy.matrix`)                                                        |

- **The creator's persona changes** (step 5): the brief follows at the next load. An edited angle is kept (it is the strategist's text); the brief then shows a quiet line "The persona changed since you edited this angle" with **Reset to persona's angle** (sets `angle` to null). A live angle simply changes.
- **The matrix changes:** USPs and the live angle follow at the next load; nothing is copied, so nothing goes stale.
- **The creator has no persona:** the script can still be created (hand-written scripts are not blocked, Q13); the brief shows "No persona yet" with a link to step 5, the USP row is empty, the angle is empty and editable.
- **The persona is deleted** (existing PL-2 rule): `persona_id` is already nulled by the composite FK behaviour of PL-3.1; the brief falls to "No persona yet".
- The brief is **one block** for saving (1.7): angle, duration and language save together.

### 1.5 Languages (E8)

- **A market's script languages** live in `wave_market_script_languages` (b): zero or more codes from `WORLD_LANGUAGES` except `en`, **at most four**. Zero rows = English only: no second column, no toggle, and the bar label reads "Script language: English".
- **Where they are set: the workspace, not the market builder (recommended, Q4).** The globe label on the market bar becomes a small **menu button** ("Script language: English + Slovak" with a chevron) that opens a multi-select of languages (built from the design system, E16). Reason: it leaves PL-2.4's market builder, its `markets_version` hash and the wave `PATCH` untouched, so the flag-off wave pages cannot change; and the label the frame draws is already in the workspace. **Who:** admin, manager and staff (the roles that write scripts), not creator or client users. Audit action `wave_market_script_languages.updated` (ids and codes only).
- **A script's language:** one code from its market's list, or null. **Default on creation:** the creator's `primary_language` if the market has it, else the first of `secondary_languages` the market has, else the **first** language of the market, else null. The strategist can change it in the brief block; changing it does not delete any text.
- **A script's texts** exist per language it has used. The editor shows English plus the script's current language.
- **Removing a language from a market** (recommended, Q5): allowed, with a confirm that says how many scripts use it ("3 scripts use Slovak. Their Slovak text is kept."). **Texts are kept**, never deleted. A script whose language is no longer in the market's list is shown **English only** with a line "Slovak is no longer a script language of this market" and a picker for another language; putting Slovak back shows the kept text again. Because the script's `language` is not a foreign key, this needs no cascade.
- **Not stored, not shown:** visual descriptions and B-roll are English only (E8).

### 1.6 Reference images (E9)

- **The sibling flow** (inventory 3): `ScriptImageStorage` (the four MIME types, key scheme `agencies/{agency}/brands/{brand}/waves/{wave}/scripts/{script}/{images|thumbs}/{imageUlid}.{ext}`), `ScriptImageService` (`init`, `complete`, `delete`, `reorder`), `ScriptThumbnailer`, `GenerateScriptImageThumbnail`, `strategy:sweep-pending-script-images`. **No PL-2.3 file changes**; the few shared helpers (`Storage::disk('media')`, the 64 KB head read) are called, not edited. The duplication is a tech-debt row (one image engine, later).
- **The lock and the total.** `init` runs inside the guard (1.7): wave lock, then **`lockForUpdate` on the script row**. Under it `liveTotals()` sums, **across every hook and line of that script**, ready rows' `size_bytes` plus unexpired pending rows' `declared_bytes`. It refuses with `wave_script_image.limit_bytes` when live plus declared exceeds `IMAGE_TOTAL_BYTES = 300 * 1024 * 1024`, and with `wave_script_image.limit_count` at the **block** limit. Two parallel inits queue on the script lock and see each other's reservation, exactly as for concepts. **No per-image cap beyond the total** (C4).
- **Types and the header check.** JPEG, PNG, WebP, GIF. `getimagesizefromstring` on the first 64 KB; the sniffed type must be one of the four and its extension must equal the key's; a stored Content-Type other than `application/octet-stream` must equal the sniffed MIME; GIF additionally must start with `GIF87a` or `GIF89a`. A failed check deletes the object and the row (`wave_script_image.invalid`).
- **GIF thumbnail and check (Q6).** The GD driver decodes **the first frame only**; the thumbnail is a 512-edge JPEG of it (transparent areas flattened on white). The same skip rule as concepts (above 32 MiB, 40 MP or 30,000 px a side: no thumbnail, the image still downloads). The original is served as is (an animated GIF plays in the viewer). **Proven at build with a real animated GIF** (gate G7); it is the one assumption not yet read.
- **Count per block (Q7):** **10**, the concept value. Worst case is bounded anyway by the 300 MB total.
- **Reorder within a block:** `PUT …/images/order` with the full ordered id list of that block (3.1).
- **Serving:** authenticated stream, `nosniff`, `private, max-age=300`, no presigned GET; thumbnails and files; the same policy ability as viewing scripts.
- **Sweeper and deletes:** pending rows expired for more than an hour (objects first, then the row, retry next run). Deleting a script, hook, line or image deletes the objects **first** (`delete_failed` otherwise) and the rows after, as concepts do.

### 1.7 Ordering, codes, the lock, and the save model (E7, E12)

**One lock order, everywhere: wave, then script.** `ScriptGuard::transaction(Wave, Script)` = `DB::transaction`, `StrategyGuard::lockWave`, then `lockForUpdate` on the script row, **re-checking `archived_at IS NULL` and the creator's slot under the lock**. Every script writer (script, hook, line, B-roll, texts, reorder, images) goes through it; a source-string test (like PL-3.1 B37) fails if a writer opens a bare `DB::transaction(`. **PL-3.3 changes the body to `StrategyTrackerSync::transaction`** (the PL-3.1 docblock already says so). The cost is that one wave's editors take turns for a few milliseconds per save; the alternative (script lock only) would save contention but would put the creator Remove and the script writes on two different lock orders. Stated, and recommended to keep.

**Positions** are contiguous `0..n-1` per parent, rewritten under the lock on every add, delete, duplicate and reorder; there is no unique key on `position` (so a reorder never trips a transient violation); reads order by `position, id`. **Codes are derived** (hook letter, line number, B-roll code) from the loaded order, never stored, so "codes renumber" is automatic and two requests cannot disagree on a code.

**Reorder rule:** the request carries the **complete ordered id list** of the parent's current children; the service refuses (`wave_script.order_mismatch`, 422) if it is not exactly the current set (a missing, extra, duplicate or foreign id). A concurrent add makes one of two requests fail cleanly, never a gap. Duplicate inserts the copy **directly after** the original (texts, B-roll rows and references' **objects** copied server-side; images count against the total and the block limit, and the duplicate is refused with the limit message if it would exceed either).

**Save model (recommended, Q1): autosave per block with a visible status, a per-block revision, and a leave guard.**

- **Blocks:** the brief (angle, duration, language), one hook, one line (with its B-roll rows, replaced as a set keyed by row ulids, and its texts in all languages, and the CTA flag). Structural actions (add, duplicate, delete, reorder, image upload and delete) are **immediate** requests, not autosave.
- **Autosave:** a block saves **1.5 s after the last keystroke, on blur, on collapse, and before any navigation** (`PUT` of the block's whole content with the block's `revision`). Status per block: Saving, Saved, **Could not save** (retried after 3 s and 10 s, then on the next edit; with **Retry**), Conflict. A header chip shows the worst of them ("Saved", "Saving…", "2 blocks not saved") **where the frame has "Last edited by … · …"**. Failed text **stays in the field**; nothing is cleared on error.
- **What PL-2 does, and why this differs:** PL-2 screens are dialogs with an explicit Save and a whole-payload `PATCH`, last write wins, no revision. The editor is one long form of up to 40 blocks; an explicit Save per block would put a button the frame does not draw on every block, and one Save for the whole script loses the work of a crashed tab. The alternative is in Q1.
- **Two people on one script:** different blocks never conflict. The **same block**: the request's `revision` is compared **inside the lock**; a stale one gets `409 wave_script.conflict` with the current block, and the block shows "{name} changed this block. **Keep mine** or **Use theirs**" (Keep mine re-sends with the new revision; Use theirs replaces the screen's text). A block deleted by someone else gives 404, shown as "Removed by someone else" (the existing `isGone` pattern). There is **no live sync or polling** in PL-3.2; structural changes by another person appear at the next load or the next request's response.
- **Unsaved work is never lost silently:** see 4.3.

### 1.8 Remove and Replace a creator who has scripts (E10)

- **Remove today** hard-deletes the `wave_creators` row (and its decisions). Scripts therefore cannot hang off that row; they keep `creator_id`, `market_id` and `number`, set `wave_creator_id = NULL` and `archived_at = now()` (the CHECK of 1.1).
- **The dialog** (the existing Remove confirm in `CreatorsStep.vue`, extended) shows when the creator has scripts: "{name} has {n} scripts." with a radio: **Archive the scripts (default)**: "They are hidden. They come back if {name} is added to this market again." or **Delete the scripts permanently**: "{n} scripts, {h} hooks, {l} lines and {i} images will be deleted. This cannot be undone." The second option is **shown only to admin and manager** (the policy `deleteInUse`/`canManage`, as PL-3.1). The request carries `scripts: archive|delete`; **without it the API refuses with 422 `wave_creator.scripts_choice_required`** (a client that does not know the choice cannot silently archive or delete).
- **Add the creator again** to the **same wave and market** (`WaveCreatorService::add`): inside the same lock, archived scripts with that `(wave_id, market_id, creator_id)` get the new `wave_creator_id` and `archived_at = NULL`. The persona is whatever the new slot has. **A different market of the same wave:** the scripts stay archived (a script is bound to its market's languages and persona); the dialog of that market says nothing.
- **Replace (ruled, Q8: changed from the recommendation):** **the scripts belong to the slot.** Today Replace updates the SAME `wave_creators` row with a new `creator_id` (read in `WaveCreatorService::replace`; the slot, its code and its persona stay). By default the scripts therefore **carry over** to the replacement: inside the lock the scripts' `creator_id` follows the slot (the composite FK is `ON UPDATE CASCADE` on the creator column, so the database moves them with the slot in one statement and a script can never point at a creator other than its slot's). The Replace dialog says "{name} has {n} scripts. They stay on this slot for {new name}." and offers the other choice, **Archive them and start fresh** (the scripts are archived under the OLD creator exactly as in Remove, before the slot's creator changes). Carry-over refuses with `wave_script.carry_over_exceeds_limit` (422) if the new creator already has archived scripts in this wave and the total would pass three; the person can choose Archive. When the new creator has archived scripts in this wave and the choice is Archive, those return to the slot (the Add-again rule). The delete option exists for Remove only.
- **The cap and archived scripts:** archived scripts keep their `number`, so the unique key counts them; a creator who returns never exceeds three.
- **Archived scripts are invisible in the rail.** One line under the rail ("**Archived scripts (n)**", only when n > 0) opens a dialog listing them by creator and number, with **Delete permanently** for admin and manager (Q14). It exists because a market that still holds archived scripts cannot be removed otherwise (1.9).

### 1.9 Step state, the market guard, concepts, empty states (E11)

- **Step state** (`WaveScriptStepState`, beside `WaveCreatorStepState`; **not** in `StrategyStepState::STEPS`): per market, "not started" (no script), "in progress" (at least one); there is **no "done"** until PL-3.3. The stepper's step 6 line shows "n scripts" (or the existing not-started look). The tracker row `ugc.scripts` stays **hand-set** (PL-3.3 connects it).
- **Workflow bar and rail status without dead controls (Q9):** the bar is **one read-only "Draft" pill** (the frame's pill style, grey dot) with no arrows, no "Waiting on client", no "Mark approved". Each rail row shows a grey "Draft" dot and text exactly as the frame's Draft row. The wave title pill "Scripts in client review" is not drawn. In PL-3.3 the bar grows to the four stages and the rail rows take the other three colours with no layout change.
- **Concepts (C6):** steps 5 and 6 are never locked. The stepper's concepts warning (`warnItems`) is today limited to step 5; it **also shows on step 6** (the same text and counts), a message, never a block.
- **Market guard (ruled, Q14):** `WaveMarketGuard` gains `scriptCountsByMarket` and `forgetScripts`. A market with creators is still refused first (a live script implies a creator). A market holding **only archived scripts can be removed**: like internal notes (PL-2.5 Q5) the removal is refused with `marketHasArchivedScripts` and the count until the request carries `confirm_scripts_deleted` equal to the total, then the archived scripts are deleted with the market (each with its own `wave_script.deleted` audit row; objects first in PL-3.2b). The composite FK is the backstop.
- **A market with no creators:** the page shows "No creators in {market} yet. Add creators in step 5." with a link; no rail rows. **Creators with no persona:** their rail rows and "Add script" work (Q13); the brief says so (1.4).
- **A wave with no campaign:** step 6 follows step 5's rule: the wave has no slots, so the same message as an empty market.

### 1.10 Roles (E13), deletes, erasure, audit, tenancy

- **Roles:** `view` any agency member; `manageScripts` (create, edit, delete a script, hooks, lines, images, languages, notes) admin, manager and staff (`CurrentAgencyRole::for !== null`); **`deleteScriptsInUse`** (permanent delete of archived scripts, and the "delete" choice on Remove or Replace) admin and manager only (`canManage`). Creator and client user types 404 as for all agency routes. New abilities on `WaveStrategyPolicy`.
- **What deleting a script means (Q10):** **permanent, immediate**, for all three roles, behind a confirm that names the script and counts its hooks, lines and images ("Delete Lucia Horváthová — Script 2? 3 hooks, 4 lines and 6 images will be deleted. This cannot be undone."). Objects first, then rows; the number is freed (the next new script takes it). It is audit-logged (ids and counts, no text). **Revisit in PL-3.3:** once a script can be sent to a client, delete of a sent script should be admin and manager only.
- **Erasure (inventory 5):** all eight tables are registered **`N/A`** (agency-authored, §3.7, the concept precedent) with `refs` listing exactly their user and creator FK columns (`creator_id`, `created_by_user_id`, `updated_by_user_id`, `uploaded_by_user_id`) and `classified` entries for the free-text columns (`angle`, `body`, `visual_description`, `description`, `original_filename`: "agency-authored; may name a person; not scanned; tech-debt 48"). **Erasing a creator keeps their scripts** (the creator row is anonymised in place; the rail shows "Deleted creator"). No executable erasure step, no scrub. `ErasureRegistrySchemaTest` and the engine tests prove it (gate G15).
- **Audit actions** (enum cases plus the `AuditActionEnumTest` list, literal payload keys of ids, counts and field names only): `wave_script.created`, `.updated`, `.deleted`, `.archived`, `.restored`; `wave_script_hook.created`, `.updated`, `.deleted`, `.duplicated`, `.reordered`; the same five for lines; `wave_script_image.added`, `.removed`, `.reordered`; `wave_market_script_languages.updated`. **No audit row per autosave** (block `.updated` is written once per save with `fields` as names only; a no-change save writes nothing and does not bump `revision`).
- **Tenancy:** `BelongsToAgency` on all eight; `agency_id` from the locked wave; every lookup names `wave_id` (and `market_id` or `script_id`) and the agency; composite FKs make a cross-wave, cross-market or cross-creator row impossible in the database.
