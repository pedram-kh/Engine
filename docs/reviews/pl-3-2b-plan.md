## C1. Data model and migrations

**No PL-3.2a migration is edited in place; five new ones are added.** The edit would be _allowed_ (nothing but local machines and CI has run them), but it is the worse choice: the migrations have run on CI, on `pl32_walk`, on `catalyst_test` and in the recorded rehearsal (`pl-3-2-migration-rehearsal.md`, "Rehearsal 2"), and editing them would force a `migrate:fresh` of Pedram's walk database and invalidate the rehearsal evidence for no gain. **How the pieces are stored or derived**

- **B-roll code: derived, never stored.** `{line number}_{row position + 1}` is computed from the loaded order by one server function (the presenter) and mirrored by one web function with a parity test over shared fixtures. Reasons: a stored code would have to be rewritten on every line reorder, line delete and row delete, and two concurrent requests could disagree on it; derived, "codes follow their line" is automatic and cannot drift. **The code is a label, not a key:** PL-3.3 comments and PL-6 upload slots point at the row's `ulid`.
- **Per-language text:** hooks keep `wave_script_hook_texts` (`field` audio or overlay, `language`); lines use `wave_script_line_texts`. A language is data (the list is the market's), so a column per language is impossible; two small tables keep every key composite. **Visual descriptions (hook) and B-roll descriptions stay single-language (English) columns for now** (Q3); an additive per-language table can be added later without touching what is built here.
- **Ordering:** `position` is contiguous `0..n-1` per parent, rewritten under the lock on every add, delete, duplicate and reorder; there is **no unique key on `position`** (a reorder never trips a transient violation); reads order by `position, id`. Hook letter and line number are derived from the position.
- **Archive and restore** only move `archived_at` and `wave_creator_id` on `wave_scripts`, so every child table follows with no code. **Delete does not follow by itself**: `ScriptArchive::deleteOne` must delete children first (images' objects, then image rows, B-roll, line texts, lines, hook texts, hooks), and a Postgres test proves the order (RESTRICT FKs refuse a wrong one).

**Expected locks.** Each `CREATE TABLE` takes `ACCESS EXCLUSIVE` on the new (unused) table only. Each foreign key takes `SHARE ROW EXCLUSIVE` on the **referenced** table for the migration transaction, which blocks writes (not reads) to it for milliseconds on an empty child: M6 `agencies`, `waves`, `wave_markets`; M7 `agencies`, `waves`, `wave_scripts`; M8 and M9 add `wave_script_lines`; M10 adds `wave_script_hooks`, `wave_script_lines` and **`users`** (the uploader column; `users` is the busy table, so this one is the lock to watch). No rewrite, no backfill, no index on an existing large table, no data change. The 5 s `lock_timeout` makes a blocked migration fail fast instead of queueing every later write behind it. **Rehearsal 3** (throwaway `pl32b_rehearsal`, printed first): `migrate`, `pg_locks` before commit, a second connection holding a long transaction on `users` and on `wave_scripts` to show the migration fails in 5 s, a `rollback` of each file, the composite FKs refusing a row that names another script's parent, the images CHECK refusing zero or two owners. Result appended to `pl-3-2-migration-rehearsal.md`.

## C3. Save and conflict design for lines and reorder

**What a block is.**

| Block    | Holds                                                                                                                  | Revision                  |
| -------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| Brief    | angle, duration                                                                                                        | `brief_revision` (exists) |
| Hook     | audio and overlay in every market language, shot type, visual description                                              | hook `revision` (exists)  |
| **Line** | the spoken text in every market language, the CTA flag, and the **fields** (shot type, description) of its B-roll rows | line `revision`           |

**Structural actions are immediate requests, never autosaved:** add, duplicate, delete and reorder of hooks and lines; add and delete of a B-roll row; image upload, delete and reorder; setting the market languages. They bump the script `revision` and write an audit row. Structural actions on a line's own rows (add or delete a shot) **also bump that line's revision** (the row set is part of the line block).

**Rules**

1. **Save (one block).** The request carries the block's revision; the server compares **inside the script lock** (`ScriptGuard::transaction`: wave, then script). A save that changes nothing writes nothing (as hooks). A real change with a stale revision is a `409 wave_script.conflict` with the current block; the editor shows "{name} changed this block" with **Keep mine / Use theirs**; **Keep mine re-sends once** with the revision it was shown (exactly `useBlockAutosave`), and a later save carries the revision the tab then holds, so a second conflict asks again.
2. **B-roll rows are never replaced as a set.** A line save carries only the rows it knows, keyed by ulid. Rows added in another tab are not touched by my save (and come back in the response); a row **removed** elsewhere makes my save a `409 broll_gone` carrying the current line, because applying text to a shot that no longer exists would be silent loss in the other direction. "Keep mine" after `broll_gone` re-sends without that row.
3. **Reorder** carries the **complete ordered id list** of the parent's current children. If it is not exactly the current set (a missing, extra, duplicate or foreign id) the server answers `order_mismatch` with the current order and writes nothing; the web says "The list changed in another tab. Your move was not applied" and shows the server order. **Reorder bumps the script revision only, never a block's revision**, because position is not part of any block.
4. **One tab reorders while another edits a line:** no conflict. The editing tab's save goes through (the line's revision did not move) and its response carries the list order, which the tab adopts only when it has no unsent reorder of its own. The reordering tab sees the edited text at its next load or next request's response (there is no live sync or polling in PL-3.2, as before). Two simultaneous reorders of the same set both succeed and the later one wins: position is not text, nothing is lost, and the audit log shows both. Stated, not hidden.
5. **A line deleted under an editor:** delete is structural and wins. The editing tab's next save answers 404; the block shows "Removed by someone else", **the text stays on screen to copy** (the existing `isGone` pattern), and the block is read-only. A reorder naming a deleted line gets `order_mismatch`.
6. **A text in a language that has just been removed from the market:** refused with `language_not_in_market`, the text stays on screen with the message "Slovak is no longer a script language of this market".
7. **Leave guard:** every line registers with the existing save registry (`useRegisterBlock`) exactly like a hook, so leaving with an unsent line asks Stay / Leave without saving.
8. **Every writer goes through `ScriptGuard::transaction`**; the source test (G14) gets the new writers added to its allowed list on purpose and fails on any bare `DB::transaction(`. One lock order everywhere: wave, then script.

## C4. Languages

- **Where set:** the market bar. The frame's plain label "Script language: English + Slovak" becomes a **menu button** that opens a multi-select of languages (built from the design system) with a confirm on removal. It lives in the workspace, so the PL-2.4 market builder, its `markets_version` hash and the wave `PATCH` are untouched and flag-off pages cannot change. **Not built in PL-3.2a**; built here. Audit action `wave_market_script_languages.updated` (codes and counts only).
- **What the editor shows:** English plus **every** language of the script's market, in the market's order. The head control (EN, one entry per local language, "Side by side") chooses what a person sees; it changes nothing stored. A market with no local language shows no control and one column (English). Layout for several languages: Q4.
- **Adding a language:** nothing existing changes; scripts gain an empty column; the estimate is unaffected until text exists.
- **Removing a language:** allowed after a confirm that counts what is affected ("3 scripts hold Slovak text, 11 texts. The texts are kept."). **Nothing is deleted.** The rows stay in `wave_script_hook_texts` and `wave_script_line_texts`; the editor, the estimate and (later) sending to the client use only the market's current languages; putting the language back shows the kept text again; permanent deletion of the script deletes them. The confirm and the count come from `GET …/script-languages`.
- **Which language the estimate counts (Q2):** recommended rule, computed on the server from the loaded blocks: for each **spoken** block (a hook's audio, a line's text) take the English text; **where English is empty take the first market language that has text**; words are whitespace-separated; `estimate = longest hook block + all line blocks`, `seconds = ceil(words / 2.5)`. Overlay, visual descriptions, B-roll descriptions and the brief are never counted. `ScriptEstimate::of($hookAudio, $lineText)` already has this shape; only the lines are passed in and the "text of a block" is chosen by the rule above.

## C5. Images

- **Reuse (inventory 3.4):** the storage helpers are called as they are (`disk`, `copy`, `head`, `deleteAll`); everything concept-shaped is a **sibling**: `ScriptImageStorage` (the four types and the key scheme `agencies/{agency}/brands/{brand}/waves/{wave}/scripts/{script}/images|thumbs/{imageUlid}.{ext}`), `ScriptImageService` (`init`, `complete`, `delete`, `reorder`, `copyForDuplicate`), `ScriptThumbnailer`, job `GenerateScriptImageThumbnail`, command `strategy:sweep-pending-script-images` with a scheduler entry. **No PL-2.3 file is edited.** The duplication is a tech-debt row ("one image engine").
- **Reservation and limits:** `init` runs inside the guard and takes the **script row lock**; under it the live totals count ready rows' real size plus unexpired pending rows' declared size **across every hook and line of the script**. Refusals: `limit_count` at **10 per block**, `limit_bytes` when live plus declared exceeds **300 MB per script**; a declared size above the total is refused before any lock. **No per-image cap** beyond the total. Two parallel inits queue on the script lock and see each other's reservation (a Postgres concurrency test, as concepts have).
- **Verify at `complete`:** the stored object's own size and MIME; the header sniff (`getimagesizefromstring` on the first 64 KB) must say JPEG, PNG, WebP or GIF and the extension in the key must equal it; a GIF must start `GIF87a` or `GIF89a`; a failed check deletes object and row (`invalid`). Presigned PUT as concepts do; the `_test` presign stand-in for tests.
- **GIF thumbnail:** GD decodes the **first frame only**; the thumbnail is a 512-edge JPEG (transparent areas flattened on white); same skip rule as concepts (above 32 MiB, 40 MP or 30 000 px a side: no thumbnail, the file still downloads, the placeholder shows). The original is served as stored, so an animated GIF plays in the viewer. **Proven at build with a real animated GIF** (gate), and confirmed again on the production PHP container before merge (must-confirm row).
- **Removal:** object first (`delete_failed` leaves the row), then the row, then the positions of the block are rewritten; audit with ids and size only.
- **Archive and restore:** images and their objects are untouched; the script's rows and keys do not move. **Carry-over on Replace:** the script rows move with the slot (existing `ON UPDATE CASCADE`), so images stay attached with no copy.
- **Permanent delete** (a script, the archive's delete, a Remove with "delete", a market purge): collect every image key of the script; **delete the objects first**; if any deletion fails, stop with `delete_failed` and nothing in the database changes (the script stays, the person retries). Under the lock, the key set is compared again with the one deleted; an image completed in between aborts with a retryable `delete_failed` rather than leaving an orphan object. The sweeper only handles expired **pending** rows (objects first, then the row, retry next run), so an object with no row is never created by design.
- **Duplicate** a hook or line copies the objects server-side; the copies count against the block and the total and are refused with the limit message if they do not fit; a failure mid-copy deletes the copies made so far.
- **Tech-debt row 40** (no virus scan or content check beyond the header sniff; **must be solved before PL-4**) applies unchanged: script images are uploaded by agency staff only in this chunk, the same exposure class as concept images, and the row is cited in the new tech-debt row for the duplicated engine.

**Reorder.** Grip handle with HTML drag and drop for the pointer, **and a full keyboard path**: Space picks up the focused handle, Arrow Up/Down moves, Space or Enter drops, Escape cancels, with `aria-live` announcements ("Line 3 moved to position 2 of 5"). The block menu always offers **Move earlier / Move later**, which is also the supported way on touch (dragging on a phone is not relied on). Images reorder inside their block the same way. B-roll rows have no handle in the frame and are not reordered.

**Focus handling: no template ref inside a `v-for`.** After add, duplicate, delete, move or collapse, focus goes where a person expects (a new line's text field, the moved item's handle, the next item after a delete). The parent keeps one state value (`focusRequest = {id, part}`); each card **watches it and focuses its own root-level ref** (a single ref per component instance, not an array of refs collected in a loop). Tested by `nextTick` and `document.activeElement` in Vitest and by one Playwright keyboard run.

**Limits near the limit only** (default, easy to change): a quiet message when a count reaches the last three of its cap (27 of 30 lines, 10 of 12 shots, 8 of 10 images in a block), when the script's images reach 80% of 300 MB, and when a text is within 20% of its length; always shown at the limit with the refusal text. No counter is shown otherwise. Strings: about 90 new keys in **all 24 locales** (the key-parity spec `scriptsKeys.spec.ts` grows from 123 keys and fails on any locale missing a key). No `v-html` anywhere in the scripts folder (an architecture test greps).

## Open questions for Pedram

Few, each with the plain question, the options, my recommendation and what it costs to change later.

**Q1. How many B-roll rows may one script hold: 12 per script, or something else?** The ruling says 12 per script, but the creator frame's own sample says "4 lines · 13 B-roll shots", and the earlier plan said 12 per line.
Options: (a) 12 per script as ruled, the frame's sample is corrected on the design side; (b) 12 per line (up to 360 per script at 30 lines); (c) a larger per-script number such as 24.
**Recommendation: (a), as ruled**, and ask the design side to change the sample to 12 or fewer. It is cheap and safe: a real script has 4 to 8 lines.
Cost to change later: **low**: one constant and its tests; the cap is a service rule, not a column or a CHECK, so no migration.

**Q2. Which language does the length estimate count?**
Options: (a) English only (what PL-3.2a built); (b) English, and where English is empty the first local language that has text; (c) the first local language, the one the creator will speak.
**Recommendation: (b).** Word counts differ between languages, so no rule is exact, but (a) shows 0 for a line written only in Slovak and (c) is wrong while a translation is half written; (b) never shows 0 for a filled line and stays close to the current numbers.
Cost to change later: **low**: one pure server function and its tests; nothing stored.

**Q3. Are B-roll descriptions (and a hook's visual description) written in English only, or in each language?** The editor frame draws one column for them and the earlier ruling says English only, but the creator frame shows B-roll descriptions in the creator's language (Slovak).
Options: (a) English only now; PL-6 shows the creator the English description (or PL-9 translates); (b) per language now (a text table for B-roll and a language column for visuals).
**Recommendation: (a)**, and decide for the creator view before PL-6 starts. Nothing built now blocks (b): a per-language table for B-roll descriptions is additive.
Cost to change later: **moderate**: one additive table, an editor change and a data decision (existing English text becomes the `en` row); no destructive migration.

**Q4. How many languages per market, and what does "Side by side" mean with more than one local language?** The Nordics market holds four countries and could want four languages; the 686 px editor cannot show five columns.
Options: (a) up to 4 local languages; the toggle has one entry per language plus "Side by side"; side by side shows English and **one chosen** local language; (b) up to 4, side by side shows **all** columns in a wrapping grid; (c) up to 2 languages.
**Recommendation: (a).** It keeps every column readable at the frame's width, needs no new layout idea and still allows the Nordic case.
Cost to change later: **low**: web layout only; the cap is a service rule (the table has no limit).

**Q5. When a creator is erased, should their scripts' reference images be deleted from storage?** Today (and in the precedent for concept images) scripts and images are kept as agency work and the creator is anonymised in place; a reference image could still show a person, and nothing scans it (tech-debt row 40).
Options: (a) keep, with the residual risk written down (as now); (b) delete the objects and rows of images in that creator's scripts at erasure; (c) keep until PL-4's scan exists, then decide.
**Recommendation: (a) now, with a tech-debt row and the privacy sentence of row 48 extended to files**, because the images are the agency's references, not the creator's data, and (b) would remove work the agency still needs.
Cost to change later: **moderate**: an erasure step that deletes objects and a registry change; no schema change.

**Q6. One walk or two?** See C10.
Options: (a) two walks, split at images (3.2b-i writing, 3.2b-ii images), each pushed on its own green CI; (b) one walk at the end.
**Recommendation: (a).** The two parts fail in different ways and the writing part is what the strategists use first.
Cost to change later: **none** to the code (the order is the same); (b) costs one longer walk.
