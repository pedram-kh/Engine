### 1.3 The slot code and the persona code: exactly what each frame shows

- **Slot code** = the black chip on the **photo**, top-left of the card: `SK1`, `SK2`, `SK3`, `SK4`, `SK5`, i.e. the **market's short code plus a running number** of the creator in the market. Fill #0b0b0c, text 12 / 700 #ededed.
- **Persona code** = the **violet-outlined chip inside the PERSONA select**: Lucia `SK1`, Martin `SK2`, Katarína `SK1`, Tomáš `SK2`. In the summary row the same codes appear in the "Persona coverage" pills (`SK1 · 2 creators`, `SK2 · 2 creators`).
- **Both are written the same way**, market short code plus a number, so **the text is identical** for Lucia (slot SK1, persona SK1) and Martin (slot SK2, persona SK2), and **different** for Katarína (slot SK3, persona SK1) and Tomáš (slot SK4, persona SK2). Only position and chip style tell them apart. Persona codes are also what PL-2.4 generates (`PersonaService::defaultCode`, market code plus the persona's slot, `Strategy/Services/PersonaService.php:324-332`), so a built wave would show the same collision.
- **Recommendation** (plan section 1.3, question Q1): generate slot codes as **market code, a dash, `C`, and a number** (`SK-C1`, `SK-C2`), editable, unique inside the market; persona codes stay `SK1`. The two can then never be equal as text, and the chips keep the frame's two different styles.

## 2. The campaign side

### 2.1 Applications

- Model `Campaigns/Models/CampaignApplication.php`; table `campaign_applications` (`2026_07_27_110000_...`): `id`, `ulid`, `agency_id` (RESTRICT), `campaign_id` (CASCADE), `creator_id` (RESTRICT), `status` varchar(32), `note`, `responded_at`. **Unique `(campaign_id, creator_id)`**: one application per creator per campaign, forever (a rejected one stays and blocks re-applying).
- `CampaignApplicationStatus`: **`pending`, `accepted`, `rejected`** (`Enums/CampaignApplicationStatus.php:41-45`). **There is no "withdrawn" status and no withdraw endpoint** (a search for "withdraw" finds nothing relevant).
- A **job post is the campaign itself**: `campaigns.listed_on_jobs_board = true` and a non-terminal status. There is no job-post model. A creator applies through `CreatorJobBoardController::apply` (region lock and brand-exclusivity checks first).
- Transitions: agency **accept** (`CampaignApplicationController::accept`, creates an `invited` assignment through `CampaignInvitationService::invite`, never an accepted one), agency **reject** (`::reject`, status only, no reason, notifies the creator by in-app row and by mail if the flag is on, touches no assignment), **auto-reject** of every pending application when the campaign becomes completed or cancelled (`AutoRejectPendingApplicationsJob`), and **convergence** (a direct invite of a creator with a pending application marks it accepted, `CampaignApplicationDecisionService::settlePendingApplication`).
- The agency applicants list (`GET agencies/{agency}/campaigns/{campaign}/applications`, `CampaignApplicationController::index`) filters on `status` only; its resource emits `creator {id, display_name, is_erased, avatar_url}` and no country or language, and its key set is pinned by a spec.

### 2.2 Invitations

- `CampaignInvitationService::invite` writes one `campaign_assignments` row, status **`invited`**, with the offer fields, audits `assignment.invited`, and dispatches `AssignmentTransitioned` (no authorisation, transaction or notification of its own).
- Direct invite: `POST .../campaigns/{campaign}/assignments` (`CampaignAssignmentController::store`): creator must be Approved **and discoverable** (else 404), then hard-blacklist (422 `assignment.blacklisted`), then availability conflict (409, acknowledgeable). A re-invite of a **declined** row re-offers on the same row (`reofferAfterDecline`); any other existing row is returned as it is.
- Creator actions: `POST creators/me/assignments/{assignment}/accept|decline|counter` (`CreatorAssignmentController`). **Accept** moves `invited -> accepted` and, **when the campaign does not require a per-campaign contract (the default, `Campaign.php:104`: `false`), chains straight to `contracted` with `contract_id` null** in the same transaction. So on a default for-a-wave campaign an accepted creator is almost always in status `contracted`, not `accepted`.
- Notifications: invite and re-invite notify the creator (in-app, plus mail behind a flag). **Accept, decline and counter notify nobody** on the agency side (no arm in `SendAssignmentNotifications`), so the agency learns of an answer only by looking at the board.

### 2.3 Assignments

- Model `CampaignAssignment` (`BelongsToAgency`, `SoftDeletes`); table `campaign_assignments`. **Unique `unique_assignment_campaign_creator (campaign_id, creator_id)`**, soft-deleted rows included. Columns that matter here: `status`, `creator_id`, `campaign_id`, `contract_id` (nullable FK), `agreed_fee_*`, offer fields, `invited_at`, `responded_at`, `accepted_at`, `posting_due_at`, `draft_due_at`, `payment_id` (no FK; payments are not built), `cancelled_at`, `cancelled_reason`, `cancelled_by_user_id`.
- `AssignmentStatus` (17 cases, `Enums/AssignmentStatus.php:73-89`) (checked for `isTerminal` and `countsAsSelected`): `invited`, `declined`, `countered`, `accepted`, `contracted`, `producing`, `draft_submitted`, `revision_requested`, `approved`, `rejected`, `completed_on_approval`, `posted`, `live_verified`, `manually_verified`, `payment_held`, `payment_released`, `cancelled`.
  - `isTerminal()`: `declined`, `rejected`, `completed_on_approval`, `payment_released`, `cancelled`.
  - `countsAsSelected()` (accepted or later, the Q4 rule of PL-1.2): `accepted`, `contracted`, `producing`, `draft_submitted`, `revision_requested`, `approved`, `posted`, `live_verified`, `manually_verified`, `payment_held`, `payment_released`, `completed_on_approval`. False for `invited`, `countered`, `declined`, `rejected`, `cancelled`.
  - `isPreSelection()`: `invited`, `countered`. `isPaymentEligible()`: `live_verified`, `manually_verified`, `completed_on_approval`.
- State machine: `CampaignAssignmentStateMachine` is the only writer of `status`; its private `commit()` runs one transaction (status, audit row, `AssignmentTransitioned` event, listeners synchronous inside it).

### 2.4 The Discover grid, cards and filters, and what can be reused

- Page `apps/main/src/modules/discover/pages/DiscoverPage.vue`, API wrapper `discover/api/discovery.api.ts`, endpoint `GET agencies/{agency}/creators/discover` (`AgencyCreatorDiscoveryController::index`). No store: local refs and `useListQueryState` (URL-backed filters, 300 ms debounced search).
- **Filters** (shared trait `Agencies/Concerns/FiltersCreatorColumns::applyCreatorFilters`, also used by the roster and the pool members list): `q` (PostgreSQL `search_vector` prefix match; SQLite `LIKE` on `display_name` and `bio`), `country` (**one** code, `=`), `language` (**`primary_language` only**, not secondary), `category` (JSON contains), `age_min`, `age_max`. **No talent-pool filter and no campaign filter on Discover.** Order: `display_name`, `id`; 24 per page on the page (25 default, max 100).
- Base query `discoverableCreators()`: `application_status = approved`, **`is_discoverable = true`**, `visibleToAgencies()` (not erased, no pending deletion), minus hard-blacklisted. **A creator who applied but set themselves not discoverable is not on Discover**, while the campaign's own accept-application path deliberately ignores `is_discoverable` (`CampaignApplicationController::accept`).
- **Card payload** `CreatorDiscoveryResource`: `id` (ulid), `display_name`, `is_erased`, `country_code`, `age`, `primary_language`, `accent`, `content_companions`, `categories`, `avatar_url`, `relationship_status`. No city, no verified, no portfolio, no secondary languages.
- **Card component** `agency/components/AgencyCreatorCard.vue` (AH-114, Discover frame 17:468): a **190 px cover**, radius 12, body padding 16, name and connection pill, location, language, at most 2 category chips plus "+N". ### 2.5 Where a creator's country and languages live

- `creators.country_code` char(2) nullable, indexed (`idx_creators_country_code`); `creators.region` varchar(160) nullable (free text); `creators.primary_language` char(2); `creators.secondary_languages` jsonb (list); `creators.accent`; `creators.categories` jsonb (list of keys); `creators.date_of_birth` (never emitted raw). `Creator` is **not** agency-scoped (it is a global table; `CreatorTenancyArchitectureTest` pins that).

### 2.6 How a market's countries (PL-2.4) match a creator

- `wave_market_countries(wave_id, market_id, country char(2))`, composite FK `(wave_id, market_id)` to `wave_markets(wave_id, id)`, **unique `(wave_id, country)`**: a country is in one market per wave. A market has one or more countries; `wave_markets` has unique `(wave_id, id)` (`unique_wave_markets_wave_id_id`), `(wave_id, code)` and `(wave_id, lower(name))`.
- The match is **`creators.country_code IN (the market's countries)`**, two capital letters on both sides (validated as `size:2` only, tech-debt row 50: `ZZ` is accepted). A creator with a **null** country matches no market. Discover's country filter takes **one** code; a market with two countries needs a list filter (new, in the picker's own controller; the shared trait is left alone).
- Nothing today enforces that a creator in a market is from the market's countries, and PL-2.4 lets the countries change at any time (M5), so country is a **filter**, not a rule (plan section 1.3).

### 2.7 The set of creators who may be picked (R5)

A creator is **eligible** for a wave when, for the wave's linked campaign, there is a `campaign_applications` row **or** a live (not soft-deleted) `campaign_assignments` row for that creator. Both tables are `BelongsToAgency`, unique per campaign and creator, so the set is two indexed lookups on `campaign_id`. Status does not exclude: an applicant whose application was rejected, or an invitee who declined, **was** invited or did apply and shows in the picker with their derived status (plan 1.4). Erased creators and creators with a pending deletion are excluded by `Creator::visibleToAgencies()` (`Creator.php:353-367`); `is_discoverable` is **not** required (see 2.4); hard-blacklisted creators are excluded as Discover does (plan question Q4).

### 3.2 The wave board's two automations and the working set

`BoardDefaults::waveAutomations()` (`Support/BoardDefaults.php:135-141`): **`assignment.invited` -> Invited** and **`assignment.cancelled` -> Dropped**, nothing else. Accepted, declined, countered, re-invited and contracted have **no** automation, which is why Accepted and Declined cards stay in Invited. The nine columns are Applied (a pseudo-column, not data), then eight data columns with `stage_key`: `invited`, `selected`, `filming`, `submitted`, `in_edits`, `client_review`, `approved`, `dropped`. The **working set** is `selected, filming, submitted, in_edits, client_review, approved` (`BoardDefaults::waveWorkingStages()`, `:149-152`).

### 3.3 The invite labels

`BoardCardResource` (`Http/Resources/BoardCardResource.php`): `invite_state` (`invited`, `accepted`, `declined`, or absent) and `invite_origin` (`invite` or `application`) are emitted **only on a wave board**, `invite_origin` only for cards in the Invited column. The origin is **derived**: the creator id is in the request attribute `boards.applied_creator_ids`, filled by `WaveInviteOrigin::remember` from one query of **accepted** application rows for the campaign. The labels (PL-1.2 review D3): Invited, Accepted invite, Declined, **Offer sent** (application accepted, creator not yet answered), Application accepted. The origin is **not stored**; the one misread case (an applicant who is later also invited separately) still has no path, and **PL-3.1 adds no second path that creates a card** (adding a creator to a wave creates no card), so the PL-3 note of 2026-11-18 ("decide whether the origin is stored once a second path to a card exists") resolves to: **still derived, no change**.

### 3.4 Where the "In wave" marker and the P8 move belong

- **Marker:** a **derived** boolean on the wave-board card resource, `in_wave`, true when the card's creator is in the wave's creator list. It is read with **one query per board load** (the creator ids of the linked wave) through a request attribute, the same way `WaveInviteOrigin` works; nothing is stored on `board_cards` (the Boards schema does not change). The Applied pseudo-column (pending applications, no card) needs the same marker on its items (plan 3.3).
- **The P8 move is not a board automation.** An automation fires on one event key and cannot read "the client approved AND the creator accepted". The move is wave logic, so it lives in the Strategy module and calls **one new method on the Boards module** that moves a card by rule (an event-style movement row with a new `triggered_event_key`, no `User` required). This is the existing event-move shape (`BoardAutomationService`), with the wave lock.
- **How it fires without a scheduled job: two synchronous triggers.**
  1. **A decision is recorded:** the decision service (inside its own transaction) calls the one function.
  2. **A creator accepts:** a **new listener on `AssignmentTransitioned`** (registered next to `CreateBoardCard` and `BoardAutomationListener`, `Campaigns/CampaignsServiceProvider.php:44-82`), acting on `assignment.accepted`, is registered like the others (the listeners are synchronous; the event is dispatched inside `commit()`), but **the plan defers its work until the accept has committed** (`DB::afterCommit`, plan section 8), so a failure cannot roll back a creator's acceptance.
     Accept can chain a second event (`assignment.contracted`) for a contract-less campaign; the listener acts on `accepted` only and the rule reads `countsAsSelected()`, so both orders and the chained case give the same result.
- **Why a lost update cannot happen** (two connections, decision and accept at the same moment): both paths take the **wave row lock first** and read the other side's fact **after** the lock, so whichever commits second sees the first's committed state and moves the card. PostgreSQL only; SQLite has no row locks. The plan's gate is a true two-connection test, as PL-2.5 A2 did.
- **The accept listener runs in the creator's request**, where no agency tenancy context is set. It must find the wave and the slot **without** the `BelongsToAgency` scope (as `WaveCampaignLink::lockWaveOfCampaign` already does, `WaveCampaignLink.php:39-46`), and nothing it writes may depend on a tenancy context.

### 3.5 The link lock today

`WaveCampaignLink::isLocked(int $campaignId)` (`Waves/Services/WaveCampaignLink.php:23-31`) (checked): true when a card of the campaign's board sits in a working column **now**. Callers: `WaveService::applyCampaign` (`WaveService.php:294`, refuses with 422 `wave.campaign_link_locked`), `WaveResource.php:60` and `CampaignResource.php:123` (the `link_locked` attribute). P10 adds the "wave has at least one creator" condition **inside this one method**, and all three callers follow. The lock UI strings (`app.waves.errors.campaignLinkLocked`, `app.waves.dialog.campaignLocked`, `app.campaigns...linkLocked`, `app.waves...locked`) all say "a creator is Selected or further", which becomes untrue and must be reworded (24 locales).

### 3.6 Finding: the existing cancel-to-Dropped automation takes no wave lock

PL-1.2's plan said a move **out of** the last working column takes the wave lock. The `assignment.cancelled -> Dropped` automation moves a card out of a working column without it. Today nothing reaches it from an agency action, so it has been harmless. **Release (section 4) holds the wave lock itself** before it cancels, so the plan does not depend on the automation locking; it is recorded so nobody relies on it.

## 4. The existing cancel action, in full (for P9)

### 4.1 The headline: there is no agency cancel action, only a state-machine method

**(checked)** A search of the Campaigns, Boards and Waves route files for `cancel` finds nothing, and a search of `apps/api/app` for `->cancel(` finds **one production caller**: `Erasure/Cancellation/CancelOpenAssignments.php:62`, which calls `$this->machine->cancel($assignment, CampaignAssignment::CANCELLED_REASON_CREATOR_ERASED, null)` for a creator whose account is being erased. There is no controller, request, policy ability or web call for it (the only `assignment.cancelled` strings in `apps/main` are notification templates for the erased-creator notice). The PL-1.2 plan's phrase "Cancel and Reject stay the real actions" and a listener comment ("every other cancellation is the agency's own act") describe an agency cancel that **does not exist as a route**. (The assignment **draft** reject, `POST .../assignments/{assignment}/reject`, is a different action: it moves `draft_submitted -> rejected`.)

So "the EXISTING cancel action" is **`CampaignAssignmentStateMachine::cancel(CampaignAssignment, string $reason, ?User $actor = null)`** (`Campaigns/Services/CampaignAssignmentStateMachine.php:600-625`) (checked). Release would be its **first agency caller**, through a new route. That is not a new cancel path (the same method, the same effects), but it is a new entry point and Pedram has not seen that distinction, so the plan asks (question Q5).

### 4.2 What `cancel()` does (every consequence)

1. **Guard:** only `$assignment->status->isTerminal()` is refused (`assignment.terminal`): `declined`, `rejected`, `completed_on_approval`, `payment_released`, `cancelled`. An empty or blank reason is refused (`assignment.reason_required`). **Every other status can be cancelled by the machine itself, including `contracted`, `producing`, `draft_submitted`, `approved`, `posted`, `live_verified`, `manually_verified` and `payment_held`.** The machine has no guard for a signed contract, delivered content or a payment state; the only such guard is in the erasure caller, which skips payment-eligible work (`CancelOpenAssignments`).
2. **One transaction (`commit()`):** sets `status = cancelled`, `cancelled_at = now()`, `cancelled_reason = <the reason>`, `cancelled_by_user_id = <actor or null>`; saves; writes an audit row `assignment.cancelled` with the **reason in the audit `reason` field** (the action requires a reason) and metadata `from`, `to`; dispatches `AssignmentTransitioned` **inside the transaction**.
3. **Listeners of that event (all synchronous, all in the transaction):**
   - `CreateAssignmentAvailabilityBlock`: acts only on `accepted`; **does nothing on cancel**.
   - `SendAssignmentNotifications`: for `assignment.cancelled` it calls `notifyAgencyOfErasedCreator`, which acts **only** when `cancelled_reason` is the fixed erasure reason and `cancelled_by_user_id` is null (`SendAssignmentNotifications.php:124` and the method) (checked). **For any other cancel, nobody is notified: not the creator, not the agency.**
   - `WriteSystemMessage`: cancel is not in its allow-list; **no chat message**.
   - `CreateMessageThread`, `DispatchPostedContentVerification`: not relevant to cancel (not read in full).
   - `CreateBoardCard`: acts on `assignment.invited` only.
   - `BoardAutomationListener`: finds the wave board's automation `assignment.cancelled -> Dropped` and **moves the card to Dropped** (movement row `triggered_by = event`, no audit row, **no wave lock**, section 3.6).
4. **What is not touched:**
   - **The contract:** `contract_id` and the `contracts` row are untouched (a contract already sent or signed stays as it is).
   - **Payment:** nothing (no payments table exists; `payment_id` has no FK; `holdPayment` and `releasePayment` throw "escrow unavailable").
   - **The creator's calendar:** the hard availability block created on accept (`CreatorAvailabilityBlock`, `kind = assignment_auto`) **is not removed**. After a Release the creator's calendar keeps a block for the dates of an assignment that no longer exists.
   - **The posting and draft due dates, the offer, the files:** unchanged.
5. **Visible after the fact:** the thread stays readable and human sends are blocked (`MessageThread::HUMAN_SEND_BLOCKED_STATUSES` includes `cancelled`); the creator's job card shows "Ended" (`JobLifecycleState`); brand exclusivity ends at once (`endsExclusivityImmediately`).
6. **Reversibility:** none. No machine edge leaves `cancelled`; a direct invite of the same creator to the same campaign returns the existing row unchanged (unique `(campaign_id, creator_id)`), and accepting a pending application against it answers 422 `application.already_engaged`. A released creator **cannot be re-invited to this campaign**.

## 5. The PL-2.5 choke point and step state, and how Creators joins it

- **The choke point is `StrategyTrackerSync::transaction(Wave, ?User, array $steps, Closure)`** (`Strategy/Services/StrategyTrackerSync.php:46-67`), **not** `around`. `around` is only on the `WaveStrategyState` contract (`Waves/Contracts/WaveStrategyState.php:45`, implemented by `StrategyWaveState`). There is **no** `ChangesStepState` trait. The enforcing architecture test is `tests/Feature/Modules/Strategy/Pl25GatesTest.php:50-80` ("B20 / A1"): a **source-string** check that eight named services contain `StrategyTrackerSync::transaction(`, and that a bare `DB::transaction(` appears only in an allow-list. It is not a model-write detector, so a new service that never opens a transaction would not be caught.
- `transaction()` locks the wave (`StrategyGuard::lockWave`, `:49`), does nothing else when strategy is off, reads the real state of the touched steps before, runs the change, drops emptied marks (rule E), reads after, and applies the F1 table through `WaveStrategyRowService::apply`, the **only** system writer of a tracker row.
- **Step state** is `StrategyStepState` (steps `usps`, `personas`, `matrix`, `concepts`; `MARKABLE = usps, personas, matrix`; `rowKey()` maps a step to a `ugc.*` key; **`stepOfRow()` returns null for `ugc.creators` and `ugc.scripts`**). Those two keys are in `WaveStepKey::STRATEGY` (renameable, not removable) but not in `REAL_KEYS`, so **the F1 table never applies to them: hand-set only, `status_source = manual`, no confirm, no chip** (`WaveStepService::applyStatus`, `:367-397`).
- **Wave and market locks:** every Strategy write takes `StrategyGuard::lockWave` first (`Wave::whereKey()->lockForUpdate()`, inside a transaction).
- **Markets:** `WaveMarketGuard` contract (`Waves/Contracts/WaveMarketGuard.php`; `personaCountsByMarket`, `conceptCountsByMarket`, `renamePersonaCodes`, `noteCountsByMarket`, `forgetMarkets`), bound only in the Strategy provider. A market is refused removal while it has personas or concepts (M6); removing deletes its completion marks and notes with counts in the audit (PL-2.5 Q5). **Creators join here**: a market with creators must also be refused removal (plan 1.7).
- **How Creators joins (design in the plan, section 1.8):** the new Creators writers go through **one** wave-lock helper of their own, today it only takes the wave lock; in PL-3.3 that helper calls `StrategyTrackerSync::transaction` with a new `creators` step and `StrategyStepState` gains a `creators` branch. Nothing already built changes.
- **Notes:** `wave_strategy_notes.step` has a **PostgreSQL CHECK** `step IN ('usps','personas','matrix','concepts')` (`2026_11_22_100001_...:58-61`). A Creators notes thread needs `creators` added: a new migration (plan 2).
- **Stepper today:** steps 5 and 6 show "Not available yet" plus the tracker status and the concept warning; `StrategyStepper.vue:32` returns `not_started` for `creators` and `scripts`.

## 6. Erasure, audit and tenancy

### 6.1 This is the first PL table that references a CREATOR

No `wave_*` table has a `creator_id` today (the registry's `refs` for every PL table list users only). `RegistryVerifier` (`Erasure/Registry/RegistryVerifier.php:89-161`) fails the build for a table the registry does not name (`:93-99`), for **any foreign key to `users` or `creators` that is not declared in `refs`** (`:101-109`, including N/A tables), and for a column-level table with an unnamed or stale column. A table-level disposition of ANON, KEEP or SCRUB-JSON is invalid (`:150-152`), so a table that holds a creator reference and wants KEEP is **column-level**, naming every column.

**Dispositions** (`Erasure/Registry/Disposition.php:11-42`): `ANON` (overwrite the column), `ERASE-ROW` (delete the row), `KEEP`, `SCRUB-JSON`, `DEL-MATCH`, `EXPIRE`, `N/A`, `CANCEL` (open assignment cancelled through the state machine).

**How a creator's erasure runs** (`Run/ErasureRun.php`): the `creators` and `users` rows are **anonymised in place, never deleted** (`creators.deleted_at` is left null; `display_name`, `bio`, `date_of_birth`, `avatar_path` and the rest are ANON; `erased_at` set). Own satellites (sessions, portfolio, social accounts, `talent_pool_creators`, availability) are deleted. **`campaign_assignments` rows are KEPT**, and an open one (not terminal, not payment-eligible) is **cancelled with reason `creator_account_erased`, no acting user** (`CancelOpenAssignments.php:58-62`), which fires the same `AssignmentTransitioned` event, so **the card moves to Dropped on a wave board** and the agency's admins and managers get an in-app notice. **`campaign_applications` rows are KEPT** with only `note` nulled. The run is **refused** for payment or delivered-work reasons (`Guards/DeliveredWorkGuard.php`).

### 6.2 Precedents and the classification this table needs

| Precedent                                                                                   | Disposition                                                  | Reason it carries                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `board_cards`                                                                               | column-level, all KEEP, `refs` `[]`                          | "Edge to an anchor; no creator data (§3.3)": the card reaches a creator only through `assignment_id`                                                                                   |
| `campaign_assignments.notes`, `agency_creator_relations.internal_notes`, `blacklist_reason` | KEEP                                                         | D-D: the deciding party's own record; the residual risk "free text that names the person" is accepted and **free text is not scrubbed by guessing** (`account-deletion-pii-map.md:46`) |
| `talent_pool_creators`                                                                      | table-level ERASE-ROW                                        | "A pure pivot; keeping it puts a ghost in a curated list": a membership with **no content of its own**                                                                                 |
| `wave_concept_decisions`                                                                    | table-level N/A, `client_name`, `note`, `comment` classified | Agency-recorded (§3.7), a third party's words typed by the agency; tech-debt row 48                                                                                                    |
| `wave_strategy_notes`                                                                       | table-level N/A, `body` classified                           | "erasing a creator does not touch it"                                                                                                                                                  |

**The wave's creator slot is not a pure pivot**: it carries the agency's own plan (slot code, persona match), and its decisions carry a client contact's name and words **about that creator**. **Recommended classification** (plan section 1.9): **`wave_creators` column-level, `creator_id` KEEP** ("Edge to an anchor": the creator row is anonymised in place and never deleted, so the id stays valid and points at an anonymous row), slot code and persona KEEP (D-D, the agency's plan), user column `added_by_user_id` KEEP as an agency-side pointer; **`wave_creator_decisions` table-level N/A**, `client_name`, `note`, `comment` classified exactly like `wave_concept_decisions`, `recorded_by_user_id` in `refs`. Not recommended: ERASE-ROW of the slot (it would delete the agency's plan and, through the composite keys, the client's decision history, on a creator's request, which the D-A and D-D decisions already decided against for the agency's records).

**What erasing a creator does to their place in a wave** (consequence of the above, to be pinned by a test): the slot **stays**; the card shows the existing "Deleted creator" label (`is_erased`, `creatorLabel`), no photo, no location or languages (the creator row is blank), the persona and slot code remain; the derived status becomes **Declined** (the open assignment was cancelled by the run, or it was already terminal); the board card moves to **Dropped** by the existing automation; the decision history **stays**, with the client's name and comment as typed. The comment is a free text that may name the creator; that is **the same accepted residual risk as `internal_notes`**, and the privacy documents need the same sentence as tech-debt row 48 (plan question Q6, with the alternative: ANON `note` and `comment` to null on the creator's erasure, which needs a new erasure selection).

### 6.3 Audit

- `Audit::log` goes through `AuditLogger::log`; `AuditAction` (`Audit/Enums/AuditAction.php`, PL cases at `:521-589`) is **`<subject>.<verb>`**; `AuditActionEnumTest` is a full-list equality test (a new case must be added to its sorted list and, if it requires a reason, to the reason-mandatory set). `requiresReason()` includes `assignment.cancelled`.
- **The PL concept decision is `wave_concept.decided`** (`AuditAction.php:574`), not `wave_concept_decision.*`. Its payload (`ConceptDecisionService.php:74-81`) is literal keys `wave`, `concept`, `market`, `status`, `has_note`, `has_comment`: **never the name, note or comment**.
- `AuditPayloadKeysGuardTest` (`tests/Feature/Modules/Erasure/AuditPayloadKeysGuardTest.php`) runs `tools/enumerate-audit-actions.php --json` and fails on any literal key not decided in `AuditPayloadKeys` (`scrubKeys`, `keptKeys`, `notPersonalKeys`) and on any non-literal payload in an undeclared file. **`creator_id` and `from_column_id` are already decided (an id)**; new keys need a group in `notPersonalKeys` in the same commit.

### 6.4 Tenancy

- `BelongsToAgency` (`app/Core/Tenancy/BelongsToAgency.php`) scopes every PL table by `agency_id` and fills it from `TenancyContext` on create (throws `MissingAgencyContextException` otherwise). All PL models use it. **`Creator` does not** (global, pinned by `CreatorTenancyArchitectureTest`). `CampaignAssignment`, `CampaignApplication`, `AgencyCreatorRelation` and `BoardCard` do.
- **There is no per-table tenancy allowlist test.** `tests/Feature/Tenancy/` holds `MissingContextTest.php` and `SetTenancyContextTest.php`; the "allowlist" is the route table in `docs/security/tenancy.md` (§4), where PL routes appear as "NOT a scope bypass" rows. New routes need rows there (the plan lists it).
- Creator ulids are global, so **tenant safety for a creator comes from the campaign**: the eligible set is built from this agency's `campaign_applications` and `campaign_assignments` of this wave's campaign. A hand-made request naming any other creator is refused by the service inside the wave lock (plan 3.2).
