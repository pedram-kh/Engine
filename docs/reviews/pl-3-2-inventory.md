## 3. What PL-2 and PL-3.1 code offers to reuse

All paths are under `apps/api/app/Modules/Strategy/` or `apps/main/src/modules/strategy/`; read in code, not run.

| Need                                 | What exists                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Use for PL-3.2                                                                                                                                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Concept image flow (API)**         | Table `wave_concept_images`: composite FK `(wave_id, market_id, concept_id)` to `wave_concepts`, `status` pending or ready with a CHECK, `expires_at`, `declared_bytes`, `size_bytes`, unique `storage_key` and `thumb_key`. `ConceptImageService::init` takes a **row lock on the parent concept** (`ConceptService::lockedConcept`, `lockForUpdate`), sums live bytes (ready plus unexpired pending, declared bytes for pending) and refuses at 10 images or 300 MB; reservation expires in 20 minutes; `complete` re-locks, checks the object, reads the first 64 KB, sniffs with `getimagesizefromstring`, requires extension and Content-Type to match; `delete` removes the objects first, then the row. `ConceptThumbnailer`: GD, 512 edge, JPEG quality 80, **skips** above 32 MiB, 40 MP or 30,000 px a side. Job `GenerateConceptImageThumbnail` (default queue, one try, 120 s, 768 MB). Sweeper `strategy:sweep-pending-concept-images` every 15 minutes (pending rows expired for over an hour, objects first). ## 4. Where a creator's languages live, and how they map to language codes

- **Creator:** `creators.primary_language` is `char(2)` nullable (one ISO 639-1 lowercase code); `creators.secondary_languages` is `jsonb` nullable, cast to an array of two-letter codes. Migration `2026_05_14_100000_create_creators_table.php` (L49-50); model `Creator.php` (cast L433). Onboarding seeds `primary_language` from `users.preferred_language` (`CreatorBootstrapService.php:73-76`). Profile and admin requests validate with `Rule::in(Locale::WORLD_LANGUAGES)`.
- **A list of languages on the server: yes.** `app/Core/Enums/Locale.php`: the 24 EU languages as ISO 639-1 codes, `UI_LOCALES` (all 24 today) and **`WORLD_LANGUAGES`** (every living ISO 639-1 code). It is mirrored in `packages/api-client/src/locales.ts` (`EU_LANGUAGES`, `UI_LOCALES`, `WORLD_LANGUAGES`) with a TS-to-PHP parity architecture test. `languageEndonym(code)` gives the name in the language itself (used by `WaveCreatorCard.vue`: "Slovenčina · Magyar"). There is no config file and no lookup table.
- **A market's languages: none today.** `wave_markets` has `name`, `code` (2 to 6 characters), `position`; `wave_market_countries` holds ISO 3166-1 countries (unique per wave). No per-country default language exists in `apps/api/app` or `apps/api/config`; **not searched in** `apps/main/src` or `packages/api-client/src` (the agent that read the API did not look there).
- **Mapping:** a creator's language and a market's script language are the **same kind of value** (a two-letter lowercase code from `WORLD_LANGUAGES`), so "the creator's own language when the market has it" is an exact string match against `primary_language`, then `secondary_languages`. English (`en`) is the base and is **not stored** as a market language.
- **Where a market's script languages are set:** a recommendation, not a fact (plan 1.5, Q4).

## 5. Erasure, audit and tenancy

- **Registry** (`app/Modules/Erasure/Registry/`): `ErasureRegistry.php`, `TableRule`, `ColumnRule`, `Disposition`, `AnonValue`, `RegistryVerifier`. Dispositions: `ANON`, `ERASE-ROW`, `KEEP`, `SCRUB-JSON`, `DEL-MATCH`, `EXPIRE`, `N/A`, `CANCEL`. A table has one table-level disposition or a per-column map; `refs` must list **exactly** the columns that are foreign keys to `users` or `creators`; `classified` explains PII-shaped columns on `N/A` tables. `ErasureRegistrySchemaTest` (L64-118) fails on any unclassified table, column or FK of the migrated schema.
- **How the precedents classify:**
  - `wave_concept_images`: `N/A`, "agency-authored (§3.7), a reference image on a concept"; `refs ['uploaded_by_user_id']`; `original_filename` noted as typed by the agency. The files are not erased.
  - `wave_concepts`: `N/A`, no user or creator column. `wave_concept_decisions`: `N/A` with `client_name`, `note`, `comment` classified under tech-debt 48.
  - `wave_strategy_notes`: `N/A`, `classified['body']` = free text an agency user typed, not scanned, untouched by creator erasure (tech-debt 48); `refs ['author_user_id']`.
  - `wave_creators`: every column `KEEP`; `refs ['creator_id','added_by_user_id']`; the reason says the creator row is **anonymised in place and never deleted**, so the slot stays and reads "Deleted creator".
  - `wave_creator_decisions`: `note` and `comment` `ANON` to null (free text **about the creator**), the rest `KEEP`; one executable step (`Selections.php:159-164`, `Steps.php:65`, phase 4c) nulls them when that creator is erased.
- **What erasing a creator does to scripts (recommended classification, to be built):** the **creator row is anonymised, never deleted**, so `wave_scripts.creator_id` stays valid and the rail shows "Deleted creator". Scripts, blocks, texts, B-roll rows and images are **kept as they are** (agency-authored creative work, the concept precedent), not anonymised and not removed. **Precedent that applies:** `wave_concepts` and `wave_concept_images` (N/A, agency-authored) for the content; `wave_creators` (KEEP, creator never deleted) for the link; **not** `wave_creator_decisions` (that text is about the person). Stated residual risk: a script's free text could name the creator; it is **not scanned**, the same class as notes and concept decisions (tech-debt 48), so the plan adds the new tables to that row rather than inventing a scrub. The creator's name on screen is read live from the (anonymised) creator row, never stored in a script.
- **Audit:** `Audit::log(action:, actor:, subject:, metadata:, agencyId:)` inside the same transaction; metadata keys are **literal arrays** (a static test, `AuditPayloadKeysGuardTest`, reads them) and hold ids, counts and field names, never text. Actions are cases of `AuditAction` (`WaveCreatorAdded` … `WaveCreatorCardMoved`, `WaveConceptImageAdded`, `WaveConceptImageRemoved`, `WaveStrategyNote*`), and `AuditActionEnumTest` holds an `$expected` list that fails on drift. A new action needs the enum case, the test list entry and (for a new key) `AuditPayloadKeys`.
- **Tenancy:** `BelongsToAgency` (global scope, `agency_id` filled from the tenancy context); services pass `agency_id` from the **locked wave**, never from the request; routes run `['auth:web','tenancy.agency','tenancy']`; composite FKs carry `wave_id` and `market_id` so nothing crosses a wave or market; `creators` itself is **not** tenant-scoped (the campaign scopes the picker). Tests that pin it: `StrategyAccessTest` (T1), `CreatorsApiTest` (B3), `CreatorsSchemaTest` (M1 composite FK, RESTRICT), `Pl25RaceTest`, plus the `Tenancy` folder.
