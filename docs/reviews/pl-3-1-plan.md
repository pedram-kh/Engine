## 8. PROD-DATA RISK (stated first, before any code)

**PROD-DATA RISK: NONE for existing production data, and no existing production table is altered. ONE runtime risk on a hot production path, with its mitigation, is stated below and needs Pedram's eye.**

**The data.** No PL migration is on `main` or in production (the first merge of `pl` creates every PL table). PL-3.1 adds **two new tables, created empty**, and **changes one constraint on a PL table that is itself new** (`wave_strategy_notes`, from PL-2.5). It adds no column to `creators`, `campaigns`, `campaign_assignments`, `campaign_applications`, `board_cards`, `users` or `agencies`.

| Table (new)              | Parents it references                                                                                                                                         | Lock taken while it is created (on live parent tables)                                              |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `wave_creators`          | `agencies`, `waves`, `wave_markets` (composite `(wave_id, market_id)`), `wave_personas` (composite, see 1.1), **`creators`**, `users` (adder, `nullOnDelete`) | SHARE ROW EXCLUSIVE on each parent for the length of the migration (milliseconds on an empty child) |
| `wave_creator_decisions` | `agencies`, `waves`, `wave_creators` (composite `(wave_id, wave_creator_id)`), `users` (recorder, `nullOnDelete`)                                             | the same, on the parents                                                                            |

**The two parents that matter are `creators` and `users`**: both are busy production tables (sign-ups, profile saves, logins). A foreign key takes SHARE ROW EXCLUSIVE on its parent, and if a long transaction already holds a conflicting lock the migration waits **and every later write to that parent queues behind the migration**. Therefore **every migration begins with `SET LOCAL lock_timeout = '5s'`**, so a blocked migration fails fast instead of stalling sign-ups, and the deploy is re-run. `statement_timeout` is not set (the statements are instant on empty tables). The locks are **measured, not asserted**: the build runs `migrate` on a throwaway PostgreSQL (`pl31_rehearsal`, section 6.5) and reads `pg_locks` before commit, as PL-2.1 M2 did; the result goes in the review ("not run" until then). Rehearsal data is synthetic only.

**In place or new files? NEW FILES.** The frozen-migration rule does not forbid editing a PL migration in place today (`pl` has never merged), but editing in place makes every developer database that already ran the file silently differ from CI; PL-2.5 chose new files for the same reason and **PL-3.1 does too**: four new files (section 2), nothing existing edited.

**The runtime risk: the accept listener (binding conditions, Pedram 2026-11-22).** The "Approved plus Accepted moves the card" rule needs a listener on `AssignmentTransitioned`, which fires inside the state machine's transaction for **every campaign in production, wave or not**. The listener:

1. **Flag guard first.** It reads `creators_scripts_enabled` and returns at once when it is off, **without reading the other two flags**. It runs **no query of its own**. _Stated limit:_ Pennant's database store answers a flag read with one `features` lookup the first time a flag is read in a request (and stores a default row for a flag it has never seen); that read is Pennant's, it is cached for the rest of the request, and it is the same read every existing flag check on this path already makes. So "zero queries" is proven as: **with the flag state already resolved in the request, the listener adds zero queries** (the test resolves it first and then counts), and **with the flag off it reads nothing but that one flag**. A literal zero would need a config-only flag, which would be a different pattern from all 14 flags.
2. **Then the cheap read.** With all three flags on, it returns after **at most one read** (the campaign's `campaign_type` and wave link, one indexed lookup) unless the campaign is `for_wave` and linked to a wave.
3. **Acts only on `assignment.accepted`.**
4. **Runs after the accept transaction has committed** (`DB::afterCommit`); it takes the wave lock and reads the committed decision and acceptance under it.
5. **Catches every `Throwable`, reports it to Sentry with ids only** (assignment id, campaign id, wave id: never a name or text), and **never changes the outcome of the accept**.
6. Runs with **no agency tenancy context** (the creator's request) and needs none.

Tests, each with a break-revert (6.1): `ListenerFlagOffRunsNoQueryTest`, `ListenerNormalCampaignAcceptUnchangedTest` (the accept's response and database writes are byte-for-byte what they are without the listener), `ListenerExceptionLeavesAcceptCommittedAndReportedTest`, plus `ListenerNoTenancyContextTest` and `ListenerOnlyAfterCommitTest`.

### 1.2 One creator per wave, not per market (settled)

A creator is **one assignment on one campaign**, and a wave has **one campaign** (1:1). The assignment has one status and one card. A creator in two markets would be one status and one card standing in two lists, with decisions that cannot say which market they were for. Markets are also disjoint by country (unique `(wave_id, country)`), so a creator matches one market by country. **Unique `(wave_id, creator_id)`.** The picker's "Already in wave" therefore means **in any market of this wave**; the chip reads "Already in wave" and its tooltip names the market when it is another one (Q12). Within a market a slot code is unique and a persona may hold any number of creators.

### 1.3 Slot code, persona code, and the market match

- **Slot code** is the label on the photo. Default: `{market code}-C{slot}` (`SK-C1`, `SK-C2`), the first free number of the market, assigned in the same transaction as the insert. Editable (2 to 10 characters, upper-cased, unique inside the market, 422 `wave_creator.slot_code_taken`). **It is kept on Replace.**
- **Persona code** is the violet chip in the PERSONA select (`SK1`). Both frames and both code families put a market code in front of a number, so the **frame's two chips can show the same text** (Lucia: slot `SK1`, persona `SK1`; inventory 1.3). The `-C` form removes the collision: a slot code can never equal a persona code. The chips keep the frame's two styles (slot: dark chip on the photo; persona: violet outline inside the select). Recommendation, question Q1.
- **The market match is a filter, not a rule.** The picker opens pre-filtered to `creators.country_code IN (the market's countries)` with one removable chip per country. Removing the chips shows every applicant and invitee, and a creator of another country can be added. Reason: PL-2.4 lets a market's countries change at any time, a creator with no country matches nothing, and an agency may knowingly book a creator from a neighbouring country. A creator is therefore **never refused for country**. Gate B11 pins both directions.

**Summary row (P5):** `total`, a count per status (a status with count 0 is omitted, as the frame draws only three pills), a count per persona **for every persona of the market** (a persona with 0 is returned with 0), and `warnings.personas_without_creator`: the persona codes with 0 creators, shown as an amber line under the row ("SK3 has no creator yet"). ### 1.5 The picker's source rule (P2, R5) and what it reuses

- **THE PICKER RULE (stated once; Pedram, 2026-11-23).** A creator appears when they **applied to or were invited on the linked campaign** (a `campaign_applications` row or a live `campaign_assignments` row; both carry `agency_id`, so another agency's rows are invisible). Being **non-discoverable does not exclude an applicant** (Q4: they applied; the picker invites nobody). A creator **never appears, and the server refuses them (422 `wave_creator.not_eligible`, one body for every reason)**, when they are: **not approved**; **erased or scheduled for deletion** (`visibleToAgencies`); **hard-blacklisted agency-wide or for this campaign's brand** (both predicates of `AssignmentInviteGate::isHardBlacklisted`, `AssignmentInviteGate.php:47`); or **blocked from this brand by another brand's exclusivity** (the existing `BrandExclusivity::excludeBlockedCreators`, `BrandExclusivity.php:136`, the SQL mirror of the apply-time `isBlocked` used at `CreatorJobBoardController.php:268`; a no-op while `campaign_brand_exclusivity` is off). **G2 finding:** the invitation gate itself checks hard blacklists, `approved`, `is_discoverable` and erasure but **not exclusivity**; exclusivity is enforced at apply time and in the job fan-out, and `JobsBoardVisibility` (creator-side: approved, rostered, not blacklisted agency-wide, job live, not hard-blacklisted for the brand, `JobsBoardVisibility.php:66-78`) deliberately does not include it. The exclusivity leg is therefore the exclusivity rule's own predicate, not the gate's. Soft blacklists stay. Tests: `CreatorsApiTest` B6 (one case per exclusion) and B5; break-reverts rows 32 to 36.
- **Enforced twice:** the candidates endpoint only lists the eligible set; and **the add and replace services re-check eligibility inside the wave lock**. A hand-made request naming any other creator (a Discover creator who never applied, a creator of another agency's campaign, a made-up ulid) is refused with the **same** 422 `wave_creator.not_eligible` and the same body for "does not exist", "not eligible" and "erased", so the endpoint cannot be used to probe the global creators table (gate B9).
- **No campaign:** `GET candidates` and every write answer 422 `wave_creator.campaign_required` (P1). The step shows the **no-campaign state** (4.1): "This wave has no campaign yet. Creators come from the campaign's applicants and invitees." with **Link a campaign** (the brand's for-a-wave campaigns that no wave uses, from the existing linkable list) and **Create a campaign** (name field; the PL-1.2 rules: draft, ugc, budget 0, no posting, board created, linked, one transaction, audited as `campaign.created`). Admin and manager can link or create (they hold the campaign abilities); staff sees the state with no buttons and the text "Ask an admin or manager to link a campaign".
- **Reuse.** The picker is a dialog over a **new endpoint** `GET .../creators/candidates` (filters `q`, `country[]`, `language`, `category`, `age_min`, `age_max`, `page`, `per_page`) that runs the **shared** `FiltersCreatorColumns::applyCreatorFilters` for `q`, `language`, `category`, age, and a new multi-country `whereIn` for `country[]`, over the eligible set. The shared trait is **not changed** (the Discover and roster behaviour and their baseline stay identical). It reuses **`AgencyCreatorCard.vue` through a `compact` variant** (4.2, Q3) and the `useListQueryState` debounce pattern. It does **not** reuse the Discover base query (that one requires `is_discoverable`; an applicant who hid themselves is still the agency's applicant, Q4).
- **Persona assign in the picker:** one optional persona for all selected (P2); "Choose per creator later" leaves each `persona_id` null. The persona must belong to the picker's market (422 `wave_creator.persona_market_mismatch`; composite FK behind it).
- **Add:** one request, **all or nothing** inside one transaction: the lock, the cap, the per-creator eligibility and "not already in wave" checks, the slot numbers, the inserts, then one audit row per creator after commit. Concurrent adds of the same creator hit the unique `(wave_id, creator_id)` and answer the same 422 `wave_creator.already_in_wave` (PostgreSQL test B12).

### 1.6 The board (P8): one function, two triggers, a table

**The marker.** `in_wave` on the wave-board card (and on the Applied pseudo-column's application items): derived, never stored, true when the card's creator has a `wave_creators` row in the wave linked to the board's campaign. One query per wave-board load through a request attribute (the `WaveInviteOrigin` pattern). Emitted **only** on a wave board with all three flags on; the normal board's payload key set is pinned and does not change (B34).

**The one move function.** `WaveCreatorBoardRules::reconcile(Wave $locked, WaveCreator $slot, string $trigger)`, in the Strategy module, called with the wave lock held. It reads, **under the lock**, the latest decision and the assignment status, finds the card and its column, decides by the table below, and moves with the **new Boards method `BoardCardMoveService::moveByRule(card, targetColumn, string $eventKey, ?int $triggeredByUserId)`** (a movement row with `triggered_by = event`, a new `triggered_event_key` of `wave_creator.selected` or `wave_creator.reverted`, **no** acting `User` required, the Q4 acceptance rule applied, and the wave lock **assumed held** and asserted). PL-6's hand-off to **Filming** joins here, as one more row of this table. Nothing else in the Strategy module writes a card.

**Triggers (no scheduled job).** (1) The decision service, after recording a decision, inside its own transaction. (2) A new listener on `AssignmentTransitioned` for `assignment.accepted`, which defers its work with `DB::afterCommit` (section 8). Both take the wave lock first and read the other side's fact after it, so whichever commits second sees the first and moves the card.

**The race, written out.** Decision (D) and accept (A) at the same moment. D: lock wave, insert decision, read acceptance (A not yet committed: "no"), no move, commit. A: commits (its transaction was independent of the wave lock), then after commit locks the wave, reads the decision (committed: approved) and acceptance (committed: yes), moves. Either order ends in Selected. The other race: two decisions at once, the second waits on the wave lock. ### 1.7 Remove, Replace, the link lock, markets, wave deletion, concepts

**Remove (P9, all three roles).** `DELETE creators/{slot}`. One transaction: wave lock, slot lock, row 15/16/17 of the table above, delete the decisions (count in the audit), delete the slot (its code and number are free again), audit `wave_creator.removed`. **Nothing on the campaign changes** (the assignment and application rows are byte-identical before and after; gate B22). **For PL-3.2:** when scripts exist, Remove of a creator with scripts asks **archive or delete**; the Remove path is the single function `WaveCreatorService::remove`, so PL-3.2 adds the question there and nowhere else.

**Replace (P6, all three roles).** `POST creators/{slot}/replace {creator}`. The same picker in single-select mode; the new creator passes the same eligibility and "not in wave" checks; the old creator is removed as above (a card in Filming or later refuses); **the slot row, `slot` and `slot_code`, and `persona_id` are kept**; the old creator's decisions are deleted (the new creator starts with none), count in the audit `wave_creator.replaced`. Replacing a creator with themselves is a 422.

**Release is not built in PL-3.1 (Q5, 2026-11-22).** The only cancel in the code (`CampaignAssignmentStateMachine::cancel()`, inventory 4) notifies nobody, cannot be undone, blocks re-invitation, leaves the calendar block and ignores contracts; that is not acceptable as a side item. It becomes **PL-3.4 "Release a creator"** (creator notified, calendar freed, contract and re-invite rules, undo window to be ruled; `production-line-sprints.md`). The action row in PL-3.1 is **Profile, Replace and Remove** only. **Remove from the wave changes nothing on the campaign** (gate B22 proves the assignment and application rows are byte-identical).

**The link lock (P10).** `WaveCampaignLink::isLocked(int $campaignId)` is true when a card sits in a working column **or** the campaign's wave has at least one `wave_creators` row (one `EXISTS` through `waves.campaign_id`). The three callers (`WaveService::applyCampaign`, `WaveResource`, `CampaignResource`) follow without change; the lock reads **now**, so Remove of the last creator can unlock. The four lock strings (24 locales) are reworded from "a creator is Selected or further" to "creators are in the wave or a creator is Selected or further" (section 7). **Add, Replace and Remove take the wave lock**, so a link change and a creator change serialise.

**Markets (Q16).** A market that has creators is refused removal (extends the M6 rule: `WaveMarketGuard` gains a creator count). **Wave deletion (Q9, G3):** **no code path deletes a wave today** (no route, no service; `Wave` uses `SoftDeletes` but nothing calls it; read at G3). The ruling "deleting a wave is refused while it has creators" is therefore implemented as a **model guard**: a `deleting` hook on `Wave` that throws `WaveRuleViolation::hasCreators()` while any `wave_creators` row exists, so any future route inherits it. It does **not** go through `isLocked` (no deletion goes through it today). Pinned by a model test and a break-revert.

**Concepts (P11).** No lock from concepts. Steps 5 and 6 stay open whatever the state of steps 1 to 4, and show the existing warning with its counts (PL-2.5), unchanged.

### 1.8 Step state (P13) and what PL-3.3 will connect

- **Not started** (per market): no creators in the market.
- **In progress:** at least one creator, and the market is not done.
- **Done:** at least one creator is **Confirmed with the client's Approved**, and **every** creator in the market is either Declined or (Confirmed **and** Approved). Persona coverage is a **warning, not a condition** (P5, P11, K1 spirit). The wave step is done when done in every market, "n of m markets" otherwise (K2). Recommendation, Q8; the alternative is "done = nobody is waiting" (no Shortlisted or Contacted), which ignores the client's say.
- **The tracker row `ugc.creators` stays hand-set in PL-3.1** (F1: `StrategyStepState::stepOfRow` returns null for it). The stepper's step 5 shows the **counts** (the frame's "4 confirmed" is derived: "3 confirmed" for the frame's data) and the tracker status chip the hand-set value.
- **Additive for PL-3.3:** the data already holds everything the rule needs (`wave_creators`, the decisions, and the derived status per slot). PL-3.3 (a) adds a `creators` branch to `StrategyStepState::read` that counts those; (b) adds `creators` to `STEPS` and `rowKey`; (c) changes the body of `WaveCreatorGuard::transaction` (today: take the wave lock) to `StrategyTrackerSync::transaction($wave, $actor, ['creators'], ...)`; every Creators writer and the listener already goes through that one helper (a source-string test, B37, keeps it so); (d) extends the listener from `accepted` to **every** transition of a wave campaign's assignments, because the status is derived from the campaign and a creator's decline changes the step without any Strategy write. **No migration is needed for (a) to (d).** PL-3.1 also adds the `creators` notes step and the stepper counts, so PL-3.3 does not touch them.

### 1.9 Erasure, audit, tenancy

- **Registry** (`ErasureRegistry`), **Q6 (2026-11-22)**: `wave_creators` is **column-level**: `creator_id` **KEEP** ("Edge to an anchor": the creator row is anonymised in place and never deleted, so the id stays valid), `slot`, `slot_code`, `persona_id`, `market_id` KEEP (the agency's plan), `refs` `['creator_id', 'added_by_user_id']`. **`wave_creator_decisions` is NOT N/A:** its `comment` and `note` are free text about the creator. It is **column-level**: `status`, `created_at`, `client_name`, `wave_id`, `wave_creator_id` and the other identifier columns KEEP; **`note` and `comment` SCRUB** (set to null) **for every decision about an erased creator**; `refs ['recorded_by_user_id']`. The erasure run gets a **new step** that nulls those two columns through `wave_creators.creator_id = subject creator` (one `UPDATE`, in the run's transaction). The status, the dates and the client name stay. `RegistryVerifier` fails the build if either table or any column is unnamed or a `creator_id` is not in `refs` (inventory 6.1); gate B26 proves the scrub with an erasure test and a break-revert. **The "accepted risk" wording is removed**: there is no accepted risk for those two columns any more; the client's **name** stays (the agency's record of a third party, tech-debt row 48 covers it).
- **Effect on a wave place when a creator is erased** (B26): the slot stays and shows the existing **"Deleted creator"** label, no photo, no location or languages; slot code and persona stay; the status is **Declined** (`cancelled`, set by the erasure run); the board card is in **Dropped** (the existing automation); the decision history stays with status, dates and client name, and **`note` and `comment` are null**.
- **Audit actions** (new cases, all in `AuditActionEnumTest`'s list in the **same commit**): `wave_creator.added`, `wave_creator.updated` (slot code or persona, with a list of changed field names), `wave_creator.replaced`, `wave_creator.removed`, `wave_creator.decided`, and one movement audit `wave_creator.card_moved` for the rule-driven move (the movement row records the event; the audit records the fact). **No client name, comment or note text in any audit row.** **Literal payload keys** (never a variable) from the set: `wave`, `market`, `slot`, `creator_id`, `persona`, `status`, `has_note`, `has_comment`, `count`, `fields`, `decisions_removed`, `assignment_id`, `from_column_id`, `to_column_id`, `trigger`, `card_not_moved`. `creator_id`, `assignment_id`, `from_column_id` are already decided (ids); the rest get one new group in `AuditPayloadKeys::notPersonalKeys` ("PL-3.1 creator slot attributes: ids, ulids, an enum value, counts and booleans; never the client's name, note or comment, never a creator's name") **in the same commit**. A test reads the written audit rows and fails if any value equals the client name, note or comment (B27).
- **Tenancy:** both models use `BelongsToAgency`; both tables have `agency_id`; every route sits in the standard stack (`auth:web`, `tenancy.agency`, `tenancy`), looks the slot up **through the wave**, and the wave through the brand and agency (other agency: 404). The creator is global, so tenant safety for a creator comes from the campaign (1.5). The accept listener, running in the creator's request, uses `withoutGlobalScope(BelongsToAgencyScope::class)` explicitly, as `WaveCampaignLink::lockWaveOfCampaign` does. `docs/security/tenancy.md` §4 gets the new routes as rows.

### Gaps closed (read 2026-11-22)

**G1. The state machine, soft deletes, campaign cancellation.**

- **`commit()` does not guard a concurrent transition** (`CampaignAssignmentStateMachine.php:642-679`): it sets `status` on the model it was given, saves, audits and dispatches, all inside `DB::transaction`, with **no row lock and no compare-and-swap** (`lockForUpdate` appears in the Campaigns module only in `AssignmentOfferEditor` and the contract controller). Each transition checks the **in-memory** status (`assertSource`). Two concurrent transitions of one assignment can therefore both pass and the later write wins. _Effect on the derived status:_ the status is **always read from the committed row at the time of the read**, so it is never wrong about what is stored; it can only lag an in-flight transition. _Effect on the board move:_ the accept listener runs **after** the accept commits and reads the committed status under the wave lock, so it moves the card only for a creator who really is accepted at that moment; a lost-update inside the machine (an accept overwritten by a concurrent cancel) is the machine's existing property, not made worse here, and recorded as tech-debt (row 54).
- **Nothing soft-deletes an assignment.** `CampaignAssignment` uses `SoftDeletes`, but a search of `app/` finds no `->delete()` or `forceDelete` on it; only the walk cleanup seeders delete assignments, with raw hard deletes (not soft). _Effect:_ the "live assignment" in the status map is every assignment row; a soft-deleted one is treated as absent (the query excludes `deleted_at`), and the map row "no live assignment" covers it.
- **Cancelling a campaign does not cancel its assignments.** `CampaignController` (status change, line ~339) dispatches `AutoRejectPendingApplicationsJob` for a completed or cancelled campaign, which rejects **pending applications** only; no code cancels assignments or moves cards. _Effect on the derived status:_ pending applicants become **Declined (`application_rejected`)** after the job runs; invited and accepted creators keep their assignment status (Contacted, Confirmed). _Effect on the board:_ no card moves. The P8 rule is unaffected.

**G2. Exclusivity and the invitation gate.**

- **The invite gate** (`CampaignAssignmentController::store`, `AssignmentInviteGate`) refuses: a creator who is not `approved` or not `is_discoverable` (404), an erased or pending-deletion creator (422 `creator.unavailable`), a **hard** blacklist by either predicate (422 `assignment.blacklisted`: agency-wide hard relation, or a non-soft-deleted brand-scoped hard row for the campaign's brand). It **warns** (409, acknowledgeable) on an availability conflict. **It does not check brand exclusivity.**
- **Exclusivity** (`BrandExclusivity`, behind `CampaignBrandExclusivityEnabled`) is enforced at **apply time** on the creator's side (`CreatorJobBoardController:268`, 422) and shown to the agency as a read-only conflict hint on applications (`CampaignApplicationController:112`) and in `CampaignExclusivityConflictController`. A creator exclusive to another brand **can be invited** and **can already be an applicant** (they applied before the block started).
- **`JobsBoardVisibility`** is a creator-side predicate (can the creator see the job): approved, rostered with the agency, not soft- or hard-blacklisted agency-wide, job live, not expired, **not hard-blacklisted for the brand** (leg 6, the same brand predicate as the gate).
- **Therefore, for the picker:** a creator **exclusive to another brand can appear** (the invite gate would not refuse them), with a read-only `exclusive_elsewhere` hint; a creator **hard-blacklisted for this brand (or agency-wide) cannot** (the gate would refuse). **One honest tension, for the record:** the ruling Q4 says non-discoverable applicants are included, and the invite gate would 404 a non-discoverable creator at first contact. I followed Q4 (the picker invites nobody; they applied or were invited already); the plan states this and Pedram can overrule.

**G3. Request classes, the board routes, wave deletion.**

- `InviteAssignmentRequest` (rules start at `creator_id` required string, offer rules from `ValidatesAssignmentOffer`) and `AcceptApplicationRequest` carry no field the Creators step needs.
- `BoardController::show` loads columns, automations, `cards.column:id,ulid,stage_key` and `cards.assignment...creator`: the **marker's creator ids** come from the card's `assignment.creator_id` already loaded, so the marker needs no extra relation. Board routes (`Boards/Routes/api.php`): show, reset, column CRUD, automations index and update, card move and movements; **no route needs to change**.
- **No wave deletion path exists** (routes list: index, store, show, update, tracker, steps, streams, campaign link); see Q9.
- **`isLocked` callers** are `WaveService::applyCampaign` (link change), `WaveResource` and `CampaignResource` (the `link_locked` flag). The campaign-side link and unlink go through the same `applyCampaign`/`detach` rule.
