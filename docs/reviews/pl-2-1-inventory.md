## 3. Markets: how a wave stores them

- **Storage.** `waves.markets` is a JSON list of two-letter upper-case codes (`array` cast on `Wave`), validated `min:1, max:20`, each `size:2`, `distinct`, `/^[A-Z]{2}$/` (`WaveController`). There is **no markets table**. A market has no id; its identity is its code.
- **So a per-market child row references a code**, not a key. It cannot have a foreign key to a market. The "market must belong to the wave" rule is therefore checked in application code under the wave-row lock (and has no foreign-key belt).
- **How markets change.** `WaveService::update()` locks the wave row (`lockForUpdate`) and may rewrite `markets`. Nothing in PL-1 stops a market being removed.
- **What happens to personas when a market is removed.** Today nothing, because personas do not exist. Without a rule the persona rows would become orphans with a market code the wave no longer lists, invisible in the tabs but still counted and still present. The plan rules it (plan §1.9): the edit is refused with 422 until that market's personas are removed. USPs are per wave, not per market, so a market change never touches them.
- **Names and display.** `MarketPicker.vue` and `constants.ts` (`MAX_MARKETS = 20`, `MENU_ABOVE_DIALOG_Z = 2500`) show how markets are listed in the edit dialog; the tabs reuse the same code-to-name helper (the exact helper name is not re-read here, §8).

## 5. Erasure, audit and tenancy for the new tables

- **Tenancy.** Each new table carries `agency_id` and the model uses `BelongsToAgency` (the global scope that filters by the current agency). Wrong-agency ids give 404. A child row is reachable only through its wave, and the controller loads the wave first (agency and brand checked), so a USP or persona ulid from another agency or another wave is a 404 even before the scope.
- **Erasure.** The registry (`ErasureRegistry.php`, around line 326) lists agency-authored tables as `NotApplicable` with a reason, user references in `refs`, and `classified` columns with a reason each. `waves` has `name` classified as "A wave title"; `wave_steps` classifies `name` the same way. `RegistryVerifier::PII_SEGMENTS` = `email, name, phone, whatsapp, address, ip, token, dob, birth, handle, agent, bio, avatar, tax, street, postal, secret`, matched on whole underscore-separated segments. **A persona column called `name` or `avatar_*` therefore must be classified or the verifier fails**; `title`, `explainer`, `core_job`, `drivers`, `needs` and `barriers` are not PII segments but are classified in the plan anyway (one line each) so a reader never has to guess.
- **Why an invented persona name is not personal data.** A persona ("Zuzana, 34, Bratislava, runs the office lunch") is a marketing archetype an agency writes about a target audience. It is not about an identified person and is not linked to any creator or user row. The plan states the reason in the registry and adds an input hint ("An invented name for the persona, not a real person") because the real risk is a user typing a real person's name; that case is handled the way every agency free-text field is (the agency is the controller of its own planning text; the table has no creator link, so a creator erasure never reaches it, and the agency can edit or delete the card).
- **How the registry treats free text.** Free-text columns are listed in `classified` with a plain reason ("A step title, not creator data", "A wave title") or not at all when their name is not a PII segment. There is no automatic scan of the content. For the new tables: `name` is classified; every free-text column carries a one-line reason.
- **Audit.** Wave actions live in `AuditAction.php` (lines 521 to 534 hold `wave.*`); the catalogue test (`AuditActionEnumTest`) lists every action, so new actions must be added there. `AuditPayloadKeys` needs a decision (personal or not) for each new payload key; the existing decisions (`name`, `stream`, `step_key`, `status`, `from_user`...) stand. Payloads must be literal arrays. The plan writes **ids, counts, colour keys and changed field names, never the card text**.
